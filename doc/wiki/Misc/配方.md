# 配方（misc）

> 本页收录自定义配方类型与配方数据，供重制时对照。

## 愚者配方（BHR 制作台，2026-11 落地）
| 项 | 位置 | 说明 |
| --- | --- | --- |
| 配方数据 | `data/richards-whimsy-mod/bhr_recipe/<制作台类型>/**/*.json` | 模组自带；按制作台分组（现有 `bhr_workbench` 与 `bhr_campfire`） |
| 解析器 | `recipe/ClassBlockHeadsRebon/BHR_FoolRecipe` | 手写 Gson 解析（不走原版 `Codec`） |
| 加载 / 查询 | `recipe/ClassBlockHeadsRebon/BHR_FoolRecipes` | 启动时一次性加载；`forWorkbench(...)`、`byId(...)` |
| 原料需求 | `recipe/ClassBlockHeadsRebon/BHR_FoolIngredient` | `item` / `tag` / `any` 三种写法 + `count` |
| 配方类型开关 | 游戏规则 `bhr_expert_recipes` | 开 = 只用专家配方；关 = 只用普通配方 |

### JSON 结构
```json
{
  "workbench": "bhr_workbench",      // 制作台类型
  "expert": false,                   // 是否专家配方（由 bhr_expert_recipes 规则切换）
  "level": 2,                        // 需要制作台达到的等级
  "order": 3,                        // 内定顺序（可选；不写 = 排在内定配方之后，按 id 字母序）
  "time": 60,                        // 制作时间（秒）
  "ingredients": [                   // 需求格（每格 = 一类物品 × N 个）
    { "tag": "minecraft:planks", "count": 2 },
    { "any": ["minecraft:cobblestone", "minecraft:blackstone", "richards-whimsy-mod:bhr_slate"], "count": 6 },
    { "item": "minecraft:string", "count": 1 }
  ],
  "container": "richards-whimsy-mod:bhr_tin_bucket",   // 容器返还（可选）：每份结算后额外返还一个
  "result": { "item": "minecraft:stone_axe", "count": 1 }
}
```
- 原料三种写法（可混用，取并集）：`item`（单件）、`tag`（整个标签）、`any`（任选其一，`#` 开头是标签）。
- `count` 可省略，默认 1；**同一格里可以是多个同类物品**（这是与工作台最大的区别）。
- **升级配方**：把 `result` 换成 `"upgrade_to": 2` —— 不给物品，直接把制作台升到该等级。
  `result` 与 `upgrade_to` 必须二选一（解析器会报错）。
- `time` 用**秒**（需求里的时间都是秒），代码里 `timeTicks()` 换成 tick。
- **`order`（2026-11 新增）**：内定顺序。写了就按它排，没写则排在内定配方之后、按 id 字母序。
  排序键 = `(level, 是否写了 order, order, id)`，实现在 `BHR_FoolRecipes#loadFromModResources`。
  ⚠️ 客户端与服务端用的是同一份数据、同一个排序，下标才对得上。
- **`container`（2026-11 新增）**：容器返还。每结算一份，除了产物再吐出一个该物品 ——
  给「水桶倒进配方、桶还得留下」这类需求用（现有：盐、煎饼 → 空锡桶）。一条配方只支持一种容器。

### 为什么不用原版配方系统
26.2 的客户端**拿不到**完整配方表（`RecipeAccess` 只剩石切机这类专门接口），
自定义配方想在客户端列出来就得自己发包。本项目改成「模组自带数据文件 + 两端各读同一份」，
界面列配方不需要额外联网（进度、选择等运行期状态仍走菜单数据槽）。
代价：暂时不能靠数据包覆盖/追加；以后要支持时把加载器换成 `SimpleJsonResourceReloadListener` 即可，
上层查询接口不用动。

## 后续规划（2026-11 约定，尚未实现）
以下四条是与需求方对齐过的路线，实现时按这里的口径做，别重新发明：

### 1. 更多制作台类型
- 数据层**已经就绪**：`workbench` 字段就是类型，`data/richards-whimsy-mod/bhr_recipe/<类型>/**` 按目录分组，
  `BHR_FoolRecipes.forWorkbench(类型)` 取。新增一台机器只需要：新方块 + 新菜单/界面 + 一份配方目录。
- 约定：**同一套逻辑、只换配方**；方块 id 直接当作 `workbench` 值（现有：`bhr_workbench`）。

### 2. 带燃料槽的制作台（**2026-11 已落地**，见下）
- 与普通制作台共用配方与制作流程，额外多一个「燃料格」与燃料消耗规则；
- 现状的容器只有 2 格（水晶 / 结果）+ 暂存原料列表，加燃料格需要：
  扩 `CONTAINER_SIZE`、菜单加槽、`pending`/`remaining` 逻辑里加「燃料不足则暂停」。
- 界面贴图已预留 `textures/gui/container/fuel_workbench.png`（尚未接线）。

**落地结果（2026-11，`bhr_campfire` 简易篝火）** —— 与上面三条规划有两处**刻意偏离**，
以实际实现为准：

- **燃料不是容器槽**。界面左列三格是「本机器收哪三种燃料」的示意，点一下从背包抽走该物品、
  折算成 tick 记在方块实体上。计价用**单位燃烧时间**：每台机器各自定义一份
  （简易篝火 15 秒/单位），表里只写「一件顶几个单位」（木棍 1 / 松果 2 / 木板 5），
  上限 10 个单位；与 `FuelValues` / `minecraft:fuel` 组件无关（需求原文：「燃料值由工作方块决定」）。
  于是 `CONTAINER_SIZE` 没扩，仍是 2（水晶 / 结果）。
- **进度改成逐 tick 累加 + 注册 ticker**。制作台那套「当前游戏刻 − 本份开始刻」的时间差模型
  表达不了「暂停」，而燃料耗尽必须能暂停、补燃料后原地续跑。代价是方块在区块加载期间每 tick 都跑
  （与服务端熔炉一致）。
- 「燃料不足则暂停」按上面的口径实现：`total > 0 && remaining > 0 && fuel > 0` 时才
  `progress++ / fuel--`，暂停期间暂存原料不退还。
- 副产品：`lit` 方块状态的贴图切换（`campfire_full` / `campfire_empty`）也由这个 ticker 维护。
- 细节见 [BHR_Campfire](../Blocks/ClassBlockHeadsRebon/BHR_Campfire.md)。

### 3. 配方排序：内定顺序 + 数据包配方补后面（**2026-11 已落地**）
- 规则：每个等级内先按「内定顺序」排，内定配方之后才是数据包定义的配方，且数据包配方**按字母排序**。
- 实现：配方 JSON 里的可选字段 `order`（内定配方显式写，数据包配方不写），排序键 =
  `(level, 有无 order ? 0 : 1, order, id 字母序)`，代码在 `BHR_FoolRecipes.loadFromModResources()` 的 `entries.sort(...)`。
- ⚠️ 客户端与服务端**必须用同一个排序**（配方栏靠下标对齐），改排序时两边别分叉 —— 两边读的是同一份 `sorted`，天然一致。

### 4. 产物 / 原料尚未注册的物品
- 现有 23 条配方引用的物品**都已在游戏里**；将来引入新物品时注意：
  配方解析在物品未注册时会抛错并被跳过（日志 `[recipe] 解析失败：<id>`，游戏不会崩），
  所以**加配方和加物品要一起提交**，否则那一条配方只是静默缺席。
- 同理，配方加载必须晚于所有物品注册（现在放在主类 `onInitialize()` 末尾）。
