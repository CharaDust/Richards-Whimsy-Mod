# 愚者模式（游戏模式 / misc）

> 本页记录「愚者模式」这个**自定义游戏模式**的规格与实现，供后续维护对照。
> 它不是方块/物品，占的是原版 `GameType` 枚举里的一格，因此收在 misc。

## 1. 规格

| 项目 | 值 |
| --- | --- |
| 枚举常量 | `GameType.BHR_FOOL_MODE` |
| 序列化名 | `fool`（`/gamemode fool`、存档 `playerGameType`、网络包都按它/它的 id 走） |
| 数字 id | `4`（原版占 0~3；网络与存档用的是这个 id，**不要改**） |
| 名称键 | `gameMode.fool` = 「愚者模式」/ "Fool Mode" |
| 简短名键 | `selectWorld.gameMode.fool` = 「愚者」/ "Fool" |
| 行为蓝本 | **生存模式**：`isSurvival()` 为 true，`isCreative()` / `isBlockPlacingRestricted()` 为 false |
| 切换器图标 | `textures/item/bhr/blockheads_icon.png`（经物品 `bhr_blockheads_icon` 呈现） |

- 行为蓝本只改了 `GameType.isSurvival()` 一处：原版所有「生存/创造/观众」的判定都走这三个
  方法（`isSurvival` / `isCreative` / `isBlockPlacingRestricted`）与
  `updatePlayerAbilities()`（其 else 分支本来就是生存档能力），因此饥饿、方块破坏、
  不掉落、不能飞行、受伤死亡等都自动与生存一致，不需要逐条改。
- 切换顺序（F3+F4）：创造 → 生存 → 冒险 → **愚者** → 观众 → 创造。

## 2. 实现：一个 classtweaker + 三组 Mixin

26.2 的 Fabric 提供了**枚举扩展**（Loader 0.19 / Loom 1.17 起），这是往原版枚举里加常量的
唯一可靠办法。三步缺一不可：

| 步骤 | 位置 | 作用 |
| --- | --- | --- |
| ① 类调整文件 | `src/main/resources/richards-whimsy-mod.classtweaker` 的 `extend-enum` | 给目标枚举补「占位常量字段」 |
| ② 枚举 Mixin | `mixin/ClassBlockHeadsRebon/BHR_FoolGameTypeMixin`（通用）、`mixin/client/…/BHR_FoolGameModeIconMixin`（客户端） | 运行期把占位字段换成真正的常量，并追加进 `values()` |
| ③ 行为补丁 | `BHR_FoolGameTypeMixin`（`isSurvival`）、`BHR_FoolGameModeSwitcherMixin`（切换器两处 `switch`） | 让行为与界面都认这一格 |

`build.gradle` 里必须有 `loom { accessWidenerPath = file(...) }`、`fabric.mod.json` 里必须有
`"accessWidener": "richards-whimsy-mod.classtweaker"`（属性名是历史遗留，指的就是 classtweaker）。

### 2.1 必须补的两处 `switch`

原版 `GameModeSwitcherScreen$GameModeIcon` 与 `WorldLoadEvent` 里有**穷举四种模式**的
`switch` 表达式（无 default）。Java 21+ 的穷举 switch 表达式遇到没有分支的第五个常量会抛
`MatchException`，所以：

- `getNext()`：愚者格 → 创造；观众格 → 愚者（否则循环永远轮不到愚者）；
- `getFromGameType(GameType)`：愚者模式 → 愚者格；
- `WorldLoadEvent.setGameMode(...)`：整条世界加载遥测跳过（原版 `send()` 本来就要求
  `gameMode != null`，跳过即不发这条遥测，不伪造值）。

全树检索过（26.2 的 73 个引用 `GameType` 的类），穷举 switch 只有上面三处。

## 3. 图标

切换器的格子图标类型是 `ItemStack`（`graphics.item(stack, x, y)`），**没有「贴图路径」这条路**，
所以要让 `bhr/blockheads_icon.png` 显示出来，必须先有一件真实物品：

- 物品 `bhr_blockheads_icon`「方块愚者徽标」（`item/ClassBlockHeadsRebon/BHR_BlockHeadsIcon`）：
  `models/item/bhr_blockheads_icon.json` → `textures/item/bhr/blockheads_icon.png`；
- 同一件物品同时是**方块愚者创造模式物品栏的标签图标**（原先暂用堆肥块），
  也放在该物品栏的最后一格。

## 4. 已知限制

1. **切换器底板宽度没变**：原版底板贴图是 125×75，五格需要 150 宽，于是第五格会左右对称
   溢出底板约 12.5 像素。要彻底解决只能改底板贴图（或把它横向拉伸），本次不动原版贴图。
2. **世界创建界面没有列愚者模式**：`WorldCreationUiState.SelectedGameMode` 是原版另一个枚举，
   要加就还得再做一次枚举扩展 + 界面适配。`selectWorld.gameMode.fool` 键已提前备好。
3. **必须双端都装本模组**：数字 id 4 与序列化名 `fool` 是本模组定义的，
   原版客户端连这种服务器会因为不认识 id 4 出问题。
4. **旧的玩家存档**：`playerGameType` 用 id 存，读档走 `GameType.byId(4)`，语义正确；
   但把装了本模组的存档带回**没有本模组**的客户端会按 id 0（生存）回退。

## 6. 两层生命模型（第一层 = 血量，第二层 = 濒死值）

### 6.1 规格

| 项目 | 值 |
| --- | --- |
| 第一层 | 原版 `health`，上限仍是 **20**（**不改 `MAX_HEALTH`**，其它模组看到的一切不变） |
| 第二层 | 濒死值 `fool_death_pool`，**固定 0~20**，存于玩家附件，随存档、按玩家自身同步 |
| 伤害顺序 | 先扣第一层；第一层见底再扣第二层；**第二层见底才死亡** |
| 濒死期间第一层血量 | `1.0E-4`（极小正值，血条上是空的，但让原版认为还活着） |
| 治疗 / 自然回复 | **先补濒死值**，补满后剩余才补生命值（原版 `heal` 没有 Player 重写，一处接管即全覆盖） |
| 图腾 | 在**第二层见底那一刀**触发原版 `checkTotemDeathProtection`；它回复的 1 点血被换算成 1 点濒死值 |
| 重生 / 进服 | 两层都填满（濒死值默认满 20） |
| 进入愚者模式 | 沿用**上次存下的濒死值**，不补血 |
| 离开愚者模式 | 只保证「至少半颗心」（`health >= 1.0`），濒死值留档，不会因为第一层见底而死 |
| 濒死表现 | 屏幕红边（复用原版世界边界警告的贴图/管线/染色公式）；行动惩罚留给「快乐值」实装 |
| 其它生物 | **没有**濒死值，完全走原版 |
| 计分板 / 血条 | 濒死时血量 ≈ 0（计分板显示 0），二层的值只由自定义 HUD 读附件显示 |

### 6.2 为什么第一层必须是 `1e-4` 而不是 0

- `LivingEntity.isDeadOrDying()` = `health <= 0 || dead`；一旦为真，`hurtServer` 开头就
  `return false`（之后再也扣不到血），`baseTick` 还会在 20 tick 后 `remove(KILLED)`——
  玩家会被当成死尸移出世界；
- 而 Fabric 的 `ALLOW_DEATH` 事件正是 `hurtServer` 里那个 `isDeadOrDying()` 的 redirect，
  所以「保留 0 血 + 拦死亡」这条路也走不通（下一次伤害会被开头的 early return 吞掉）。

因此第一层停在 `1.0E-4`，第二层归零时把**真实结算值**放行，原版死亡流程
（死亡消息 / 击杀归属 / keepInventory / 极限模式 / 图腾）原样接管。

### 6.3 实现清单

| 位置 | 作用 |
| --- | --- |
| `misc/…/BHR_FoolHealth` | 常量、濒死值附件（`persistent` + `syncWith(…).targetOnly()`）、伤害/治疗/图腾/模式切换的处理函数、每 tick 兜底修复 |
| `mixin/…/BHR_FoolHealthDamageMixin` | `@Redirect` **`Player#actuallyHurt`** 里的 `setHealth(health - dmg)`（玩家受伤不会走 `LivingEntity` 那份，Player 整段重写了） |
| `mixin/…/BHR_FoolHealthLivingMixin` | `heal(F)V` 改道（先补濒死值）+ `checkTotemDeathProtection` 返回 true 时换算 |
| `mixin/…/BHR_FoolHealthGameModeMixin` | `ServerPlayerGameMode#changeGameModeForPlayer` 返回处对账（进/出愚者模式） |
| `mixin/client/…/BHR_FoolHealthVignetteMixin` | 濒死红边：挂在 `Hud#extractCameraOverlays` 的 TAIL（不挂在 `extractVignette`，否则会被 `options.vignette()` 开关吞掉） |

**同步零成本**：濒死值用 Fabric 的「可同步附件」（`AttachmentSyncPredicate.targetOnly()`），
客户端 `player.getAttached…(POOL)` 直接读，不需要自己写网络包 —— 以后 精力 / 快乐 / 环境
也可以复用同一个机制。

## 7. 自定义 HUD（左侧生命条 barL）

### 7.1 贴图与坐标（所有 png 均 80×9，同一画布直接叠加）

| 图层 | 文件（`textures/gui/sprites/hud/`） | 画布内 x |
| --- | --- | --- |
| 图标 | `bhr_barl_icon_health` / `_blinking` / `_hardcore` / `bhr_barl_icon_death` | 0 … 8（9 px） |
| 长条 | `bhr_barl_empty` / `_full` / `_death` / `_blinking` | 14 … 63（50 px） |
| 伤害吸收框 | `bhr_barl_absorbing` | 13 … 64（52 px） |

> **资源名必须全小写**：原素材名是 `bhr_barL_*`，而 1.21+ 的 `Identifier` 路径只允许
> `[a-z0-9/._-]`，大写 `L` 会让客户端在 `Hud` 类初始化时直接抛
> `IdentifierException: Non [a-z0-9/._-] character in path`。故左侧一律改为
> `bhr_barl_*`（箭头也从 `barR` 更正成 `bhr_barl_arrow_*`）；`bhr_barr_*` 只留给真正的
> 右侧资源条（饥饿 / 精力 / 环境 / 氧气：长条 16…65、箭头 0…14、图标 71…79）。
> 以后从设计稿导出时请直接用小写文件名。

### 7.2 绘制规则

- 屏幕坐标：`xLeft = guiWidth / 2 - 91`，`y = guiHeight - 39`（与原版血条同一行）；
  以上表格里的 x 直接加在 `xLeft` 上。
- 绘制顺序（底 → 顶）：
  - **正常**：`empty` 铺满 50 px → `full`（宽度 = 当前生命比例，**连续值不取整**）；
  - **濒死**：左侧按**剩余濒死值**画 `empty`，右侧按**已消耗部分**画 `death`
    （例：12/20 → 左 30 px 空槽 + 右 20 px 黑；濒死值越少，黑色从右往左吃得越多），
    再叠 `full`（此时≈0）；
  - `blinking`（原版节奏闪烁）→ `absorbing`（有吸收值时画 13…64 的线框，
    **宽度按吸收值占 20 点的比例截断**：`round(absorption / 20 * 52)`，最小 3 px，
    即 4 点吸收只画 10 px 的括号，20 点才是一整圈；不补右侧封口）；
  - 图标：底图标 `icon_health`（濒死时换成 `icon_death`）；
    `icon_health_blinking` 与 `icon_health_hardcore` 都是**叠加层**，不替换底图标。
- `blinking` 覆盖段：扣血时盖「丢失段」`[fill, oldFill)`，回血时盖「新增段」`[oldFill, fill)`；
  闪烁计时直接用原版 `Hud.healthBlinkTime / displayHealth`（`extractHearts` 的入参
  `blink` / `oldHealth`），频率与原版一致。
- 宽度换算：`floor(clamp(value / max, 0, 1) * 50)`，所以 0.0001 点血显示 0 px（濒死时条是空的），
  3.7 点血就是 9 px。

### 7.3 实现方式（为什么不整个接管 `extractPlayerHealth`）

原版把「闪烁计时 / displayHealth 延迟 / 护甲条 / 载具血量」都放在 `extractPlayerHealth`，
只有心形是子方法 `extractHearts` 画的。本模组只注入 `extractHearts` 的 HEAD 并取消它：
护甲条、载具血量、原版那套闪烁计时全部保留，且 `xLeft` / `yLineBase` / `oldHealth` /
`blink` 等参数可以直接用，不需要 shadow 任何私有字段。

## 9. 快乐值（happiness）与盔甲行

### 9.1 位置

`yLineBase`（血条行）之上依次两行，行距 10 px（与原版护甲/血量间距一致）：

| 行 | y | 素材 |
| --- | --- | --- |
| 盔甲 | `yLineBase - 20` | `bhr_barl_icon_armor` + 共用 `empty`/`full` |
| 快乐值 | `yLineBase - 10` | `bhr_barl_icon_happiness` + 共用 `empty`/`full` |
| 生命 | `yLineBase` | `bhr_barl_icon_health` 等（原样） |

原版盔甲条由 `Hud#extractArmor` 画在 `yLineBase - 10`，本模组在 HEAD 处取消它，
改由同一套素材画在 `yLineBase - 20`（把 -10 让给快乐值）。

> **注意**：这两行正好落在原版**聊天栏**的区域里（聊天从 `guiHeight - 48` 往上堆）。
> 有聊天消息时它们会被聊天的半透明黑底盖住、看起来像"变暗/缺一块"，聊天淡出后恢复正常。
> 原版盔甲图标本来也在同一块区域，这是位置本身决定的，不是渲染 bug。

### 9.2 数值

- 范围 **0 ~ 20**；
- 上限 = `min(20 − 饥饿惩罚, 20 × 精力系数, 20 − 环境惩罚, 当前生命值)`，其中
  `饥饿惩罚 = max(0, (10 − 饥饿值) / 2)`（饥饿 0 → 上限 15；饥饿 ≥10 → 上限 20），
  `精力系数` 见 [§16.4](#164-精力值--快乐值上限)（精力 ≥8000 → 1；3000 → 0），
  `环境惩罚` 见 [§17.7](#177-环境值--快乐值上限)（环境值 ≥80 → 0；每少 5 点 −1；0 → 16）；
  **多个来源同时生效时取最小值**，所以**血不满时快乐值上限也不会满**；
- 回复 / 回落：未到上限时**每 2 tick +0.1**；超过上限时**同样每 2 tick −0.1 慢慢降回**
  （饥饿造成的上限下降属于这一类）；
- **例外：生命值下降导致的上限下降是瞬时的** —— 血少了，快乐值当场被压到新上限；
- 存储：持久化 + 按玩家自身同步的附件 `richards-whimsy-mod:happiness`（客户端血条直接读）。

### 9.2.1 快乐值这一行的箭头

画在快乐值行（`xLeft + 65`，`yLineBase - 10`），规则与生命值箭头同源但更简单：

| 情况 | 箭头 |
| --- | --- |
| 按回复速度上升 | **1 个正向**，0.4+0.4 渐变闪烁 |
| 按回复速度回落（饥饿压低上限） | **1 个负向**，同上 |
| 生命值压低上限（瞬时损失） | **`ceil(损失 / 2)` 个负向**（上限 5），立即 0.1 s + 渐隐 0.4 s |

判定方式（客户端，不需要额外发包）：每帧比较快乐值变化量 —— 单帧跌幅 > 0.5 视为"瞬时损失"，
0.02 以上的正向/小幅变化视为"正按回复速度移动"（保持 300 ms 以免 2 tick 的节奏断闪）。

### 9.3 行走速度 与 挖掘速度

**行走速度**：`Attributes.MOVEMENT_SPEED` 上加 `ADD_MULTIPLIED_TOTAL` 修饰符（transient，每 tick 刷新）：

| 快乐值 | 修饰符 | 实际移速（基础 0.1） |
| --- | --- | --- |
| ≥ 10 | 移除 | 0.1（100%） |
| 5 | −0.4 | 0.06（60%） |
| 0 | −0.8 | **0.02（20%）** |

**挖掘速度**：`mixin/…/BHR_HappinessMiningMixin` 在 `Player#getDestroySpeed` 的返回值上乘一个系数，
`系数 = 1 - 0.04 × (20 - 快乐值)`（满 20 不惩罚，0 点只剩 **20%**）。
乘在返回值上而不是加 `MINING_EFFICIENCY` 修饰符，才是「减少 4%」而不是「减 0.04 点」；
挖方块的速度就是这一个方法的返回值，客户端预测与服务器校验都会经过它，所以两端口径自动一致。

### 9.4 实测（服务端日志）

- 快乐值 0 → 移速 `0.0200`、修饰符 `-0.800` ✓（正好 20%）
- 快乐值 2 → `0.0360`、`-0.640` ✓（1−0.08×8）
- 饥饿 0 时上限 = 15；血量被饿到 2 时上限跟着降到 2（`min(上限, 生命)`）✓
- 回复速率：10 tick 正好 +0.5（每 2 tick +0.1）✓
- **饥饿压低上限 → 慢慢回落**：饥饿 5（上限 17.5）时 20 → 19.5 → 19.0 → 18.5 → 18.0 → 17.5，
  每 10 tick 掉 0.5，期间一直是 `neg=1` 的闪烁箭头 ✓
- **生命压低上限 → 瞬时**：生命 20 → 10 的那一帧，快乐值 20 → 10，
  箭头 `neg=5`（= ceil(10/2)）✓，随后随生命回复 `pos=1` 闪烁上升 ✓
- 重生 / 进服：快乐值补到上限（进服只夹到上限，不凭空回满）
- **挖掘速度**（石头、空手，`getDestroySpeed` 返回值）：
  `20 点 → 1.0000`、`10 点 → 0.6000`、`0 点 → 0.2000`、`0.5 点 → 0.2200` —— 连续、按比例 ✓

### 16.3 吃东西补精力的挂点（26.2 的食用链）

26.2 已经没有 `Player#eat`，吃由 `minecraft:consumable` 组件驱动：
`Consumable#onConsume` → 把身上所有 `ConsumableListener` 挨个回调 →
`FoodProperties#onConsume` 里才真正 `player.getFoodData().eat(this)`。

所以 `BHR_EnergyFoodMixin` 挂在 **`FoodProperties#onConsume` 的 RETURN** 上：

- 一叠食物被吃掉的那一次**只回调一次**（不像 `FoodData#eat` 有两个重载）；
- 参数里现成就有 `stack`（判断是不是咖啡樱桃）与 `user`；
- `Consumable#onConsume` 里那个 `forEach` 在 `isClientSide()` 判断**之外**，
  客户端也会回调一次监听器 —— 所以 mixin 自己挡掉 `level.isClientSide()`，
  否则客户端那份数值会和服端打架。

补充量取的是 `FoodProperties.nutrition()` + `FoodProperties.saturation()`：
26.2 的 `saturation` 已经是**绝对饱和度**（`FoodData#add` 直接加这个数），
所以直接相加，不再乘饥饿值。

### 16.4 精力值 → 快乐值上限

精力低于 **8000** 时快乐值上限开始线性下降，到 **3000** 时降到 **0**：

```
系数 = clamp((精力 − 3000) / (8000 − 3000), 0, 1)
精力上限 = 20 × 系数
```

最终上限仍由 `BHR_Happiness#cap` 统一收口：

```
上限 = min( 20 − 饥饿惩罚, 20 × 精力系数, 20 − 环境惩罚, 当前生命 )
```

即「饥饿、精力、环境各给一个上限，取最小的那个，再被当前生命压一头」——
**血不满时快乐值上限也不会满**。精力上限是随每 tick 消耗**连续**变化的，
下降速度（≈0.08 点/秒）慢于快乐值的回落速度（1 点/秒），
所以实际表现是「快乐值跟着上限一路往下走」，走的是既有的「慢慢降回上限」分支。

### 17.2 数值模型

范围 **0 ~ 100**，与快乐值同一套「先算目标值、再按固定速率靠拢」的写法：

```
target = clamp(100 − 各项扣分之和, 0, 100)
每 tick：value 朝 target 走 0.1 点（= 2 点/秒），不跳变
```

> **为什么是 2 点/秒而不是快乐值的 1 点/秒**：黑暗里目标值**自己**每秒也往下沉 1 点
> （基础 50 + 每秒 +1），若环境值也只走 1 点/秒就永远追不上、一直差着 50 点。
> 取 2 点/秒后，「100 → 0」与「黑暗里第 50 秒目标值见底」正好同时到达。

### 17.3 扣分表

每一项都是**独立账本**，条件消失的那一 tick 立刻清零 —— 也就是需求里的「立即返还」。

| 条件 | 扣分 | 数据来源 |
| --- | --- | --- |
| 脚下这格**方块光与天空光都为 0** | **50 分，且每 1 秒再 +1 分**（向下取整到整秒） | `level.getBrightness(LightLayer.BLOCK/SKY, pos)`（原始光照，不看时段变暗） |
| **夜里且没有方块光**（有效天空光被压到最低档 4） | **80 分** | `原始天空光 − level.getSkyDarken()`，见 [§17.8](#178-夜晚80-分) |
| 正**淋雨** | 50 分 | `level.isRainingAt(pos)`，见下 |
| 泡在**岩浆**里 | 100 分 | `player.isInLava()`；有**抗火药水**时不扣 |
| **着火** | 每 1 秒 5 分（0.25/新 tick 累加） | `player.isOnFire()`；有**抗火药水**时不扣 |
| 埋在**细雪**里 | 50 分 | `player.isInPowderSnow` 或脚下那格是 `minecraft:powder_snow` |

- 黑暗那 50 分**不是**「每秒重新扣一次」，而是一个随停留时间增长的累计值：
  进黑暗第 1 秒就是 50 分，第 2 秒 51 分……离开有光的地方立即归零；
- 「夜晚 80 分」与「黑暗 50+ 分」**互斥**：黑暗那条要求<b>原始</b>天空光为 0（被方块封死），
  夜晚那条要求原始天空光还在（露天/透光）、只是被时段压暗，两条不会同时成立；
- 抗火药水对**岩浆 + 着火**两项同时生效（与需求一致）；
- 细雪按**方块**判定，不依赖「是否在冻结」——站在雪面上（脚在雪上一格）不算。

### 17.4 「淋雨」怎么判定（照抄原版炼药锅）

`Level#isRainingAt(pos)` 就是 `precipitationAt(pos) == RAIN`，也就是原版炼药锅
（`LayeredCauldronBlock#handlePrecipitation` / `CauldronBlock#shouldHandlePrecipitation`）
吃到的同一份判定，四个条件缺一不可：

1. `level.isRaining()`（天气在下雨）；
2. `level.canSeeSky(pos)`（那一格能看到天）；
3. `getHeightmapPos(MOTION_BLOCKING, pos).getY() <= pos.getY()`
   （头顶直到建筑高度上限没有挡雨的方块 —— 用的是原版 MOTION_BLOCKING 高度图，
   和炼药锅蓄水、蓄细雪完全同源，所以花草/火把这这类不挡雨的方块不算遮挡）；
4. 生物群系 `getPrecipitationAt` 返回 **RAIN**（返回 SNOW = 下雪，不扣分）。

位置取**脚所在格**，另外再查一次**包围盒顶部**那一格（原版 `Entity#isInRain` 的做法；
那个方法是 private，这里自己拼同样的双点判定）。

### 17.7 环境值 → 快乐值上限

环境值低于 **80** 时开始压快乐值上限，**每少 5 点 −1 点**（连续换算）：

```
环境惩罚 = max(0, (80 − 环境值) / 5)
环境上限 = 20 − 环境惩罚
```

| 环境值 | 环境惩罚 | 快乐值上限 |
| --- | --- | --- |
| 100 ~ 80 | 0 | 20 |
| 75 | 1 | 19 |
| 60 | 4 | 16 |
| 40 | 8 | 12 |
| 20 | 12 | 8 |
| **0** | **16** | **4** |

- 环境值归零时快乐值上限正好是 **4**（20 − 80/5），与需求里给的验算一致；
- 换算取连续值（环境值 79 → 上限 19.8），与饥饿惩罚 `(10 − 饥饿值)/2` 的写法一致；
  若想要「攒满 5 点才掉 1 点」的硬阶梯，把 `happinessPenalty` 的结果向下取整即可；
- 这一项与饥饿、精力一样只是**上限**，最终仍与其它来源、当前生命取最小值
  （见 [§18](#18-快乐值机制总览)）。

### 17.8 夜晚（80 分）

**条件**：有效天空光被压到最低档（`NIGHT_SKY_MAX` = **4**）且**方块光为 0**。

26.2 的天空亮度不再是「白天固定 15」，而是走环境属性
`EnvironmentAttributes.SKY_LIGHT_LEVEL`：夜里它降到 **4**，
`ServerLevel#tick` 每 tick 调 `Level#updateSkyBrightness()` 换算成
`skyDarken = 15 − 4 = 11`。于是**露天**格子的有效天空光

```
有效天空光 = 原始天空光(15) − skyDarken(11) = 4
```

白天 `SKY_LIGHT_LEVEL = 15` → `skyDarken = 0` → 露天有效天空光 15。
天亮后该属性从 4 往回升（约每日 **22331** tick），有效值 > 4，这一项**立即返还**
（与其它扣分项一样是「条件一消失就清零」）。

| 时段（约） | `SKY_LIGHT_LEVEL` | `skyDarken` | 露天有效天空光 | 该项 |
| --- | --- | --- | --- | --- |
| 白天 0 ~ 12800 tick | 15 | 0 | 15 | 不扣 |
| 夜里 13670 ~ 22331 tick | **4** | **11** | **4** | **−80** |
| 黄昏 / 黎明过渡 | 15 → 4 → 15 | 0 → 11 → 0 | 同属性值 | 有效值 > 4 时不扣 |

- **不用自己数 tick**：判定直接读当前有效天空光，所以 `/time set`、雨天、
  自定义维度时间线、睡觉跳时间都自动正确（tick 窗口只是它的自然结果）；
- 与「黑暗 50+」互斥（见 §17.3 的说明）：
  - 洞里（原始天空光 0）：只吃黑暗那一条；
  - 夜晚露天：只吃这一条；
  - 夜晚的屋檐下半露天（原始天空光被压到 1~4）：按夜晚算 —— 反正都没有天光；
- 夜里再叠加下雨 = 80 + 50 = 130 → 目标值直接夹到 **0**（下限）。

#### 实测（2026-11-15，Carpet 假玩家，高空平台 y=201，无光源）

| 时刻 | 时钟 tick | 光照(方/天) | skyDarken | 有效天空光 | 环境值 | 目标值 | night |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `/time set 18000` 后 | 18038 | 0/15 | **11** | **4** | 96.3 | **20** | **true** |
| +1 s | 18058 | 0/15 | 11 | 4 | 94.3 | 20 | true |
| +8 s | 18198 | 0/15 | 11 | 4 | 80.3 | 20 | true |
| `time set 6000` 后 | 6708 | 0/15 | **0** | **15** | 100.0 | **100** | **false** |

- 目标值正好是 `100 − 80 = 20` ✓；
- 环境值以 2 点/秒朝目标值走（96.3 → 94.3 → …）✓；
- 拨到正午那一 tick，`skyDarken` 立刻变 0、`night` 变 false、目标值回到 100 ✓；
- 顺带确认了 26.2 的 **`skyDarken` 在服务端也是每 tick 刷新的**
  （`ServerLevel#tick` → `updateSkyBrightness`），否则这条判定在服务端会永远读 0。

### 17.9 环境值这一行的箭头

**恒 1 个**，方向跟着「正在上升还是下降」：

| 状态 | 箭头 | 素材 |
| --- | --- | --- |
| 环境值在**上升**（朝目标值爬） | 1 个增加箭头（朝左） | `bhr_barr_arrow_1` |

- **方向靠客户端自己比对前后两帧的数值**得出（`updateEnvironment`），不需要额外发包 ——
  目标值是服务端算的，客户端只知道「现在这个数在往下走」；
- 单帧变化阈值 0.02（环境值每 tick 走 0.1，帧率再高也够用），

## 18. 快乐值机制总览

> 把前面各节散落的规则收在一处，改数值时照这张表核对。

### 18.1 数值与存储

| 项目 | 值 |
| --- | --- |
| 范围 | **0 ~ 20**（`BHR_Happiness.MAX`） |
| 当前值 | 持久化 + 按玩家自身同步的附件 `richards-whimsy-mod:happiness` |
| 初始 / 重生 | 补到当前上限（新生一条命直接给满上限） |
| 进服 | 只夹到上限，不凭空回满 |
| 非愚者模式 | 不推进，直接复位成 20（于是移速/挖掘惩罚自然为 0 = "没有快乐值"） |

### 18.2 上限（目标值）：四个来源取最小值

```
上限 = min( 20 − 饥饿惩罚, 20 × 精力系数, 20 − 环境惩罚, 当前生命 )
```

| 来源 | 公式 | 极端值 |
| --- | --- | --- |
| 饥饿值 | `饥饿惩罚 = max(0, (10 − 饥饿值) / 2)` | 饥饿 ≥10 → 20；饥饿 0 → 15 |
| 精力值 | `系数 = clamp((精力 − 3000) / 5000, 0, 1)` | ≥8000 → 20；≤3000 → **0** |
| 环境值 | `环境惩罚 = max(0, (80 − 环境值) / 5)` | ≥80 → 20；0 → **4** |
| 当前生命 | `min(…, health)` | 血不满 → 上限跟着血走 |

> 「取最小值」这条是需求定的规矩：任何一项都能单独把上限压到很低，
> 但**没有任何一项能把别人的压低结果抬回去**。

### 18.3 当前值怎么变

| 情况 | 变化 |
| --- | --- |
| 低于上限 | 每 2 tick **+0.1**（= 1 点/秒），直到上限 |
| 高于上限（饥饿 / 精力 / 环境把上限压低了） | 每 2 tick **−0.1** 慢慢降回上限 |
| **生命值下降**导致上限下降 | **瞬时**压到新上限（血少了就是少了，不慢慢降） |

### 18.4 效果

| 项目 | 规则 |
| --- | --- |
| 行走速度 | `Attributes.MOVEMENT_SPEED` 上 `ADD_MULTIPLIED_TOTAL` 修饰符（transient，每 tick 刷新）：<br>快乐值 ≥10 → 无修饰符；<br><10 → 每少 1 点 −8%，0 点时移速只剩 **20%** |
| 挖掘速度 | `Player#getDestroySpeed` 返回值乘系数 `1 − 0.04 × (20 − 快乐值)`，0 点只剩 **20%** |

### 18.5 HUD

左侧血条**上一行**（`yLineBase − 10`），图标 `bhr_barl_icon_happiness` + 共用
`bhr_barl_empty` / `bhr_barl_full`；箭头画同一行右侧（`xLeft + 65`）：

| 情况 | 箭头 |
| --- | --- |
| 按回复速度上升 | 1 个正向，0.4+0.4 渐变闪烁 |
| 按回落速度下降 | 1 个负向，同上 |
| 生命值压低上限（单帧跌幅 > 0.5） | `ceil(损失 / 2)` 个负向（上限 5），立即 0.1 s + 渐隐 0.4 s |

### 18.6 本轮新增 / 变动

- 2026-11-15：上限来源从「饥饿 + 生命」扩到「饥饿 + 精力 + 环境 + 生命」，统一在
  `BHR_Happiness#cap` 里取最小值；
- 精力、环境两项的上限变化都是**连续**的，所以表现上快乐值是跟着上限一路往下滑，
  走的是「慢慢降回上限」分支（不是瞬时压下去）；只有**生命值**那一路是瞬时的。

### 8.1 数量

| 来源 | 箭头 |
| --- | --- |
| 生命恢复每级 | +1 正向 |
| 自然回血（饥饿 ≥18 且血未满） | +1 正向 |
| 快速自然回血（饥饿 20 且饱和度 &gt;0） | 合计 +3 正向 |
| 中毒每级 / 凋零每级 | +1 负向 |
| 饥饿值 = 0（正在掉血） | +1 负向 |
| 瞬时伤害 | 每 2 点伤害 +1 负向（`ceil(damage/2)`） |
| 上限 | 正负各 5 个（素材只有 1~5） |

### 8.2 闪烁（全部基于 `Util.getMillis()`）

- **单方向常驻**：0.4 s 由 1 渐隐到 0，再 0.4 s 由 0 渐显到 1；
- **正负同时**：两组交替 —— 前 0.4 s 正向渐隐、后 0.4 s 负向渐隐；
- **瞬时伤害**：立即满不透明 0.1 s，再用 0.4 s 渐隐到无；这段时间正向让位
  （对应「火焰里吃东西：先负，随后转正」）；
- 箭头的闪烁是 **alpha 渐变**，与 `bhr_barl_blinking`（原版频率硬闪）不是一回事。

### 8.3 瞬时伤害从哪来（不发包）

客户端每帧比较 `health + 濒死值` 的总量，掉多少按 `ceil(drop/2)` 折算；
愚者模式下第一层空了继续受伤只掉濒死值，总量照样在掉，表现一致。
如果掉血来自中毒/凋零（已经有常驻负向箭头），则不再叠加瞬时箭头，避免重复计数。

### 8.4 验证记录

- 状态机（日志逐 5 tick 采样）：中毒 II → `neg=2`；自然快速回血 → `pos=3`；
  两者同时 → 正向/负向 alpha 交替（`0.60/0.00 → 0.00/0.99 → 0.74/0.00 → 0.00/0.48 …`）；
  饱和度耗尽后 `pos` 由 3 降到 1（快速回血退化为普通回血），符合规则。
- 像素：自然回血 3 个箭头 = 18 px；一次掉 10.3 血 = 5 个负向箭头 = 30 px（触上限）。
- **未做的验证**：中毒/凋零在愚者模式下走濒死值时的箭头（逻辑一致，需实战）。

## 19. 创建世界界面：第五个游戏模式 + 专家模式按钮

### 19.1 规格

- 「创建世界 → 游戏」页的游戏模式循环按钮里，**创造模式后面**多一挡 **愚者模式**；
  循环顺序：生存 → 极限 → 创造 → 愚者 → 生存。
- 选中愚者模式时，该按钮的**悬浮提示**就是愚者模式的描述文案
  （原版这个界面里每挡模式的说明都走这条路，见 `selectWorld.gameMode.creative.info`）。
- 选中愚者模式时，页尾**多出一枚「专家模式」按钮**，循环 「关 → 开 → 自定义」，默认**关**；
  每挡各有一条悬浮文案。
- 「开 / 关」= 世界创建成功前**执行一次**「开启 / 关闭专家模式」；「自定义」= **什么都不做**。
- 「游戏规则」页面里那条 `bhr_expert_mode` 只代表**初值**，不代表进去后执行什么动作。

### 19.2 实现：一个 classtweaker + 三个 Mixin

| 文件 | 目标 | 作用 |
| --- | --- | --- |
| `richards-whimsy-mod.classtweaker` | `WorldCreationUiState$SelectedGameMode` | `extend-enum ... BHR_FOOL`（第三处扩展） |
| `mixin/client/.../BHR_FoolGameModeChoiceMixin` | 同上（enum mixin） | 常量 `BHR_FOOL("fool", GameType.BHR_FOOL_MODE)` |
| `mixin/client/.../BHR_FoolGameTabMixin` | `CreateWorldScreen$GameTab` | ① `@ModifyArg` 给 `withValues` 追加第五挡；② `@Inject TAIL <init>` 追加专家模式按钮 |
| `mixin/client/.../BHR_FoolCreateWorldMixin` | `CreateWorldScreen` | ① `createWorldAndCleanup` HEAD 执行一次预设；② `createFromExisting` TAIL 还原愚者挡位；③ `@Unique` 字段承载挡位 |

两个关键点（都是字节码核对过的）：

1. **`@ModifyArg` 必须写 `ordinal = 0`**：`GameTab.<init>` 里 `withValues` 被调用**两次**
   （游戏模式、难度），擦除后描述符完全一样
   （`withValues([Ljava/lang/Object;)LCycleButton$Builder;`）。字节码里游戏模式那次在前。
   另外还加了「数组首元素必须是 `SURVIVAL`」的运行期校验兜底。
2. **`GameTab` 不保存外部 `CreateWorldScreen` 引用**（26.2 用 nestmate 直连私有字段，
   没有 `this$0`），所以外部实例只能从**构造器实参**拿 —— `@Inject` 的处理器第一个参数就是它。

### 19.3 「执行一次」是怎么做到的

`onCreate()` → `WorldOpenFlows.confirmWorldCreation(...)` → `createWorldAndCleanup(..., Optional<GameRules>)`。
在 `createWorldAndCleanup` 的 HEAD 调 `BHR_GameRules.applyExpertModePreset(rules, expert)`：

- 写 `bhr_expert_mode`（true / false）；
- 照预设表把每条细调条目写成专家 / 普通挡位。

这正是玩家手敲 `/gamerule richards-whimsy-mod:bhr_expert_mode true|false` 时
`BHR_GameRules` 监听器做的那两件事，所以**存档里的结果完全一样**。
区别只是触发者：创建世界时还没有 `MinecraftServer`，所以 `GameRules.set(..., null)`
（写值不回调）直接写值。「读盘不重放」契约不受影响。
