# 游戏规则（misc）

> 本页收录模组注册的**游戏规则**与「专家模式」预设协调机制，供重制时对照。
> 规则属于存档级配置，不是方块/物品的附属，因此收录在 misc。

## 1. 现有规则

三条都是**布尔**规则，默认 `FALSE`。「专家挡位」= 打开专家模式时会被写成的值。

| 规则 id（省略命名空间 `richards-whimsy-mod:`） | 含义 | 默认 | 专家挡位 |
| --- | --- | --- | --- |
| `bhr_expert_mode` | 专家模式开关：**一键把下面几条写成专家预设**，本身只是个调节工具 | FALSE | —（它自己不写） |
| `bhr_decaying_leaves_no_drop` | 枯萎的树叶**直接消失、不掉落** | FALSE | **TRUE** |
| `bhr_legacy_hunger_consumption` | 饥饿消耗回到 **1.8 水平** | FALSE | **TRUE** |

- 完整 id 带命名空间（26.2 的规则就是命名空间化的），因此命令要写成
  `/gamerule richards-whimsy-mod:bhr_expert_mode true`
- 所有规则都出现在**世界创建界面的「杂项」分类**里，也可以在那里直接开关

## 2. 专家模式只是个「批量调节工具」

这是本机制的**核心契约**，四条一起看：

1. **只在手动改 `bhr_expert_mode` 时**才把细调条目写成对应预设；
2. **关闭时强制写 FALSE**（回到普通挡位），不记忆打开前的历史值 —— 关闭后的状态必须可预测；
3. **单独改细调条目不影响专家模式开关**：先开专家模式、再把某条细调条目调回普通挡位，专家模式的状态不变。
   它就是给没时间逐条调规则的玩家准备的快捷方式，不是锁；
4. **从存档读盘不重放**：世界加载时规则值是直接反序列化出来的，
   **不会**因此触发一次预设覆盖 —— 也就是说，上次手动调过的细调条目下次进游戏仍然保留。

想复原成「和专家模式一致」的状态，再开一次专家模式即可。

## 3. 规则存在哪

| 问题 | 答案 |
| --- | --- |
| 存在哪个文件 | `world/data/minecraft/game_rules.dat`（**命名空间是 `minecraft`**，不是本模组） |
| 会不会污染 `level.dat` | **不会**。26.2 起游戏规则已经不在 `level.dat` 里，我核过实测存档：`level.dat` 里搜 `game_rules` 零命中 |
| 要不要改 `server.properties` | **不要**。规则是存档级数据，与 `server.properties` 无关 |
| 和原版规则的关系 | 与本模组的三条同处一个文件（`minecraft:game_rules` 这个 SavedData）；实测该文件里 62 条规则、其中 3 条是本模组的 |

## 4. 客户端同步的能力边界

- 规则值在玩家**登录时**随 `ClientboundGameRuleValuesPacket` 下发，
  **但那条路有权限门槛**：原版 `sendGameRuleValues()` 先查 `COMMANDS_GAMEMASTER` 权限，
  **非 OP 客户端拿不到**（只打一条警告日志）；
- 运行期改动**不会**推给已经登录的客户端：原版只对少数几条规则做特殊同步，
  自定义规则不在其中。

因此：**服务端逻辑（掉落份数 / 树叶 / 饥饿 / 将来 BHR 自定义工作方块）完全不受影响；
需要客户端知道时得自己发包**（目前没有这样的需求）。

## 5. 中英名与说明

引擎实际查的键是 **`gamerule.<命名空间>:<路径>`**（**带命名空间、带冒号**），
说明键是它加 `.description`。缺了键**不会报错**，界面直接显示裸 key。

| 键 | 用途 | 示例（`bhr_expert_mode`） |
| --- | --- | --- |
| `gamerule.<ns>:<path>` | 规则**名称** | `gamerule.richards-whimsy-mod:bhr_expert_mode` |
| 名称键 + `.description` | 规则**说明** | `gamerule.richards-whimsy-mod:bhr_expert_mode.description` |

实际发出的键由 datagen 从规则 id 现算，并**同时写三种形状**（带冒号 / 带点 / 仅路径）
各配 `.description`，作为解析路径未知时的 parity 保险；确认界面文字正常后可以收紧。

⛔ **踩坑记录（2026-10，连错两次，都只能靠进游戏发现）**：

1. **第一版**写成 `gamerule.<ns>:<path>` —— 形状是对的，但**没写 `.description`**
   （说明另起了一个独立键 `gamerule.<id>`），于是名称与说明都查不到；
2. **第二版**以为键要「照抄原版」的 `gamerule.<path>` camelCase 形式
   （`gamerule.bhrExpertMode`）—— **错**。核对原版 jar 后确认：`GameRules` 的注册路径是
   snake_case（`allow_entering_nether_using_portals`），而 camelCase 的
   `allowEnteringNetherUsingPortals` **在 jar 里根本不存在**；`Identifier` 本身也不做大小写转换
   （`toLanguageKey()` 只是把 namespace 与 path 用 `.` 拼起来）。
   这一版不仅没修好，还把第一版本来能命中的名称键丢了；
3. 结论：**不要去转 camelCase**，**必须写 `.description`**，**键要带命名空间和冒号**。

排查手法：界面显示的那个裸 key **就是引擎在查的键** —— 把它原样抄进 lang 即可，不需要猜。

## 6. 传统饥饿值消耗：具体回退了哪些条目

`bhr_legacy_hunger_consumption` 开启时，下列消耗回到 **1.8** 的值。这些值是
`FoodConstants` 里的**编译期内联常量**（全 jar 除它自己没有任何类引用），
所以只能在每个调用点注入，无法通过改字段或数据包实现。

| 条目 | 26.2 | 1.8 | 被改的版本 |
| --- | --- | --- | --- |
| 游泳 / 水下行走 / 水面行走 | 0.01 /m | **0.015 /m** | 1.11 |
| 步行 | 0.0 /m | **0.01 /m** | 1.11（步行在此不再影响消耗） |
| 潜行 | 0.0 /m | **0.01 /m** | 1.9 砍半 → 1.11 归零 |
| 破坏方块 | 0.005 /方块 | **0.025 /方块** | 1.11 |
| 跳跃 | 0.05 /次 | **0.2 /次** | 1.11 |
| 疾跑中跳跃 | 0.2 /次 | **0.8 /次** | 1.11 |
| 攻击（含刺击） | 0.1 /次 | **0.3 /次** | 1.11 |
| 饥饿效果 | 0.005 /级/tick | **0.025 /级/tick**（= 0.5 /级/秒） | 1.11 |
| 疾跑 | 0.1 /m | 0.1 /m | **不变**，不注入 |
| 受伤 | 按伤害类型数据驱动 | — | **本次不回退**，仍随数据包/模组走 |

量级参考（一整个鸡腿 = 4.0 消耗值）：疾跑 0.1/m → **40 米**一个鸡腿；
步行 / 潜行 0.01/m → **400 米**一个鸡腿 —— 后两条在游戏里要走上百米才看得出变化。

## 7. 现状与限制

- 三条规则**已实现并在专用服务端验证过**：注册成功、落盘为 `game_rules.dat` 里的三条条目、
  运行期改 `bhr_expert_mode` 会连锁写细调条目、读盘不重放
- 传统饥饿值的 10 个注入点**已核对是否命中**（把 `require` 临时改成 1 启动无误），
  疾跑 / 潜行 / 步行三条已由玩家在游戏内实测确认；**游泳与跳跃尚无游戏内实测**
- 语言键已按**实测命中的形状**修正（`gamerule.<ns>:<path>` + `.description`，见 §5），
  但修复后仍未请玩家复查界面文字 —— 修复前那一版是错的，所以这一版也要再看一眼

## 8. 预告：专家模式之后会影响的条目

以下是设计意图，**尚未实现**，列在这里是为了让「专家模式」这个概念有完整轮廓：

- 方块掉落物**份数**（未持有合适工具掉 1 份；持有则极限/专家 2 份、其余 3 份）
- BHR **自定义工作方块**的配方与制作时间（原版工作方块不受影响）
- 生命值机制（为将来的「愚者模式」预留）
- 其他

其中**树叶掉落机制已实现**，见 [BHR_TreeLeavesPine](../Blocks/ClassBlockHeadsRebon/BHR_TreeLeavesPine.md)：
它读的是细调条目 `bhr_decaying_leaves_no_drop` 本身，而不是 `bhr_expert_mode` 开关。

## 9. 重制注意

- **不要**为 BHR 的模式再造一套「存档自定义数据文件」：26.2 的游戏规则已经独立成
  `game_rules.dat`，天然满足「不污染 `level.dat`」与「不改 `server.properties`」两条要求
- 「专家模式」不要实现成**真相源**（例如让所有判定都去读它）：它是调节器，
  判定应读**具体条目**，否则玩家单独把某条调回普通挡位就会失效
- 规则 id 是命名空间化的，`/gamerule` 必须带 `richards-whimsy-mod:` 前缀
- 语言键**也带命名空间和冒号**（`gamerule.<ns>:<path>`），并且**必须另写 `.description`**；
  键写错不报错、只显示裸 key，所以只能靠进游戏看。细节与两次翻车见 §5
- BHR 的饥饿值回退是**4 个 Mixin 类、10 个注入点**，清单与踩坑见 [Mixin](./Mixin.md)
