# 青金石灯（方块）
{`rdt_lapis_lamp`}
## 特点简介
一盏**分侧**的灯：玩家看到它发出 15 级光、真的照亮周围；而在服务端的一切方块与实体逻辑里，它的亮度是 **0**。
于是它可以做**明亮的刷怪竞技场**（看着亮、照样刷怪），也可以在**视觉上照亮冰雪建筑而不融化冰**。
## 构造
父级：红石灯

> ⚠️ 「父级」只指**属性表**（硬度、爆炸抗性、声音等）。本方块**不接收红石信号** ——
> 本体继承 `Block`，刻意**不**继承 `RedstoneLampBlock`（继承它会白拿 LIT 状态与红石响应）。
> 这与参考模组一致：1.12.2 Random Things 的两盏灯也直系 `BlockBase`，红石响应在彩虹灯那边。

## 渲染
- 常规渲染（`block/cube_all`）。它自己**不需要** `emissiveRendering`：光是由光照引擎给的
  （客户端引擎里这一格就是 15），所以方块自身与周围都按正常光照渲染。

## 备注
- **能力阶梯：第 5 级「Mixin」**（层 M）。0~4 级都不行，核心原因是**光照强度在 26.2 里是一个
  两侧共用的 int**（`BlockStateBase.lightEmission`，状态构造时由 `Properties.lightLevel` 求值一次并缓存，
  拿不到世界/侧别），而**玩家的"被照亮"只等于客户端光照引擎的 BLOCK 层数值** ——
  `emissiveRendering`/`getLightEmission` 只能让方块自己（以及相邻面 4 个采样里的 1 个）变亮，
  是 1 格级效果，做不出 15 格的场。
- **实现（三个 Mixin，与 [石英灯](RDT_LampQuartz.md) 共用）**：
  1. `RDT_LampLightEmissionMixin` → `BlockLightEngine.getEmission`：本引擎里这盏灯发多少光 ——
     **客户端 15 / 服务端 0**（石英灯正好相反）。侧别看的是**引擎所属的 Level**
     （`chunkSource.getLevel().isClientSide()`），不能看环境侧：单人游戏客户端与内部服务端同进程同 ClassLoader。
     原方法里那句 `storage.lightOnInSection` 守卫用公开 API 等价复刻
     （`ChunkSource.getLightEngine().lightOnInColumn(SectionZeroNode)`）。
  2. `RDT_LampLightSyncMixin` → **两侧对齐**（在光照数据真正换上去之后按本侧规则修）：
     - 客户端：光照数据**完全由服务端光照包喂**（`applyLightData → queueSectionData`），
       而服务端引擎里青金石灯是 0 ⇒ 包里没有它的光，会覆盖掉客户端本地的 15 级光，所以要**补回来**；
       同一处也负责把石英灯在服务端算出来的那 15 级光**抹掉**。
     - 服务端：两盏灯的状态发光值都是 0，原版 `propagateLightSources` 不把灯当光源 ⇒
       区块从盘上载入（含升级前的旧存档）时，石英灯的光要靠这一手补上；青金石灯在服务端本来就是 0，此处的
       `checkBlock` 对它是空操作。
     - 时序：`queueSectionData` 记下收到 BLOCK 数据的区块段，在**这一轮 `runLightUpdates` 末尾**
       （数据是在末尾 `swapSectionMap()` 才真正上位的，早一步会被抹掉）对"够得着这些区块段的灯"
       各调一次 `checkBlock`，让引擎用自己的传播把光补回来/抹掉 —— 遮挡、其它光源共存都由引擎算，**不做任何近似**。
  3. `RDT_LampIndexMaintenanceMixin` → 灯位置索引的失效（`LevelChunk.setBlockState`；26.2 的
     `Block.onPlace` 只在服务端调，客户端那条路必须靠它）。
- **服务端为什么不用额外动作**：本方块状态发光值是 0，而另一条登记光源的路径
  `BlockLightEngine.propagateLightSources` 直接读 `state.getLightEmission()` —— 它本来就不把这盏灯当光源；
  服务端唯一问发光等级的地方（`getEmission`）返回 0 ⇒ **服务端引擎里真的没有它**。
  所以引擎数值、存档、其它 mod 读到的都是"这里没有光"，不是"被我们忽略掉"。
- **参考实现（1.12.2 Random Things，已停更）**：它用一个覆写 + 客户端自愈就做到了同一件事 ——
  `getLightValue(state, world, pos)` 里按侧别返回 15/0，再在客户端 `randomDisplayTick` 里
  `if (world.isRemote && world.getLight(pos) == 0) world.checkLightFor(BLOCK, pos)` 自愈。
  两处差别：①1.12.2 的 `getLightValue` 能拿到世界（分侧），26.2 的 `lightLevel` 不能 ⇒ 只能打在引擎发光查询上；
  ②1.12.2 的客户端**自己算光照**（光照只随区块包下发），26.2 的客户端光照由服务端包喂 ⇒ 自愈从"保险"变成"必需"。
  **参考模组同样需要自愈**这一点，反过来印证了这条路线。
- **已排除的走法**：在服务端查询出口"把灯附近的光忽略掉"（近似）—— 光照是最大值场、减不掉某一盏灯的贡献，
  只能按距离猜，结果是**灯旁的真实光源（火把等）在服务端一起失效**；石英灯那边还会**穿墙**。
  RDT 是原版附加模组、混用是常态（灯 + 火把 + 两种灯），所以不走近似。
  把光放进 sky 层也不行：天色会缩放 sky 光（夜里不亮），且 `getBrightness(SKY)` 参与刷怪判定。
- **踩坑记录（本项目实测）：`@Shadow` 不会去父类找字段。**
  `chunkSource` / `storage` 都是父类 `LightEngine` 的 `protected` 字段，第一版按 `@Shadow` 写，
  起专用服务端做冒烟测试时立刻炸出来（日志 WARN，游戏继续跑）：
  `InvalidMixinException: @Shadow field chunkSource was not located in the target class ...BlockLightEngine`。
  **改法**：改用构造器捕获 —— `BlockLightEngine` 的构造器自己收得到 `LightChunkGetter`，
  在构造器 `RETURN` 处把「本引擎属于哪一侧」与 `chunkSource` 存进 `@Unique` 字段，
  `getEmission` 只读字段（顺带比每次做 `instanceof` 判断更快）。
  另一处守卫 `storage.lightOnInSection` 是 `protected`、跨包调不到，改用公开 API 等价复刻：
  `ChunkSource.getLightEngine().lightOnInColumn(SectionZeroNode)`。
  冒烟测试把三个注入点临时改成 `require = 1` 跑了一遍专用服务端（`runServer`）：
  注入全部命中、区块光照初始化无异常（日志无本模组 Mixin 的任何失败提示）。
- **无头验证方法**（只跑专用服务端、不需要客户端）见 [石英灯](RDT_LampQuartz.md) 的「验证方法」一节：
  `light` 谓词走的就是服务端光照引擎，配 `forceload` + 密封石室就能把「服务端逻辑里的亮度」读出来。
  实测结论：青金石灯那一格 = **0**，石英灯那一格 = **15**，
  而**紧挨青金石灯的火把在服务端照常生效**（近似做法会在这里翻车）。
- **验证状态（2026-10-10）**：**客户端侧已由你在游戏内实测正常**；**服务端侧用上面的无头装置验过**
  （灯那一格 = 0、紧挨它的火把照常生效）。下面这份清单留作回归测试用（改动光照相关代码后再走一遍）：
  - 黑暗处放一盏：**它自己和周围 15 格内看起来都被照亮**；F3 看光照显示应该也是亮的（客户端侧）；
  - 在它照亮的范围里**仍然会刷怪**（可以做刷怪竞技场）；旁边的冰/雪**不融化**；
  - 白天黑夜都不受天色影响（晚上应该是亮的）；
  - **和火把混用**：灯旁边放火把，火把在服务端照常生效（这是本实现与"近似做法"的分水岭）；
  - 拆掉灯后光正常消失；**走动 / 重开存档 / 走远再回来**之后光都应该在（自愈生效的证据：
    若自愈失效，走远再回来时灯会变暗）。
  - 日志里若出现本模组 Mixin 未命中的提示，说明目标方法结构变了，功能会静默失效（见上面第 5 级说明）。
