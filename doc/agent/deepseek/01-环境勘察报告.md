### 3.2 架构特点（对升级是好消息）

- **扁平化 + 低耦合**：几乎每个功能方块/物品一个独立类，类之间主要通过静态字段和 `OnInit()` 互相引用（[readme.md](../../../readme.md) 第 10-11 行自称的设计目标）。
- **统一初始化入口**：所有模块都在 [RichardsWhimsyMod.java](../../../src/main/java/com/rcdmake/whimsy/RichardsWhimsyMod.java) 第 64-133 行被显式调用，没有反射扫描。→ 迁移时可以**逐个文件地修**，改完一个就少一个报错。
- **注册样板高度重复**：`registerItems(...)` / `registerBlocks(...)` / `register_StatusEffect(...)` 这类私有静态方法在每个类里复制粘贴，且几乎都是同一个模式：
  ```java
  Registry.register(Registries.X, new Identifier(RichardsWhimsyMod.MOD_ID, name), obj)
  ```
  → 这正是 1.21+ 改动最集中的地方（`Registry.register` 签名、`Identifier` 构造、`FabricItemSettings`/`FabricBlockSettings` 废弃），但**改动模式统一**，适合脚本化/批量替换 + 人工复核。

### 3.3 `src/main/cpp/dataGen`（非 Java 的自制数据生成器）

- 一个 C++ 小工具（`main.cpp`、`state_base.cpp`、`sorce/lang/*`、`sorce/state/*`），输入 `res/lang.csv`、`res/reglist.csv`、`res/state.csv`，输出 JSON（`write_json.o`、`write_rawjson.o`）。
- 目录里带有编译产物（`.o`、`.exe`）与 Dev-C++/小熊猫式工程文件（`dataGen.dev`、`makefile.win`、`dataGen_private.rc`、`app.ico`）。
- **判断**：这是作者为批量生成 `blockstates`/`models`/`lang` 而自建的辅助工具，**不参与 Gradle 构建**（`src/main/cpp` 不在 Java 源集内）。
- **升级影响**：它生成的 JSON 需要跟随 26.2 的 `pack_format` 与模型/blockstate 语法变化（例如 1.21.4+ 的物品模型定义、1.21.5+ 的渲染相关字段）。升级期间**不要在它上面做重构**，只需在需要时补字段。

### 4.2 最脆弱的 6 处代码（升级时优先处理）

按「跨越 1.20.5→26.2 变更次数 × 代码复杂度」排序：

1. `function/ClassDEV/Render/DEV_OverlayRenderer.java`（361 行）—— 原生 `GL11.glEnable/glBlendFunc/glDisable` + `RenderSystem.setShader` + `BufferBuilder`/`Tessellator` 手写顶点。**26.2 的 OpenGL→Vulkan 后端切换直接冲击这里**（见 02 号文档 §3.6）。
2. `recipe/ClassDEV/DEV_SimpleWorker_R.java`（142 行）—— `Recipe<SimpleInventory>` 接口在 1.21 后被泛型化/重构（`Recipe<T extends RecipeInput>`），`getResult(DynamicRegistryManager)`、`craft(...)`、`read(PacketByteBuf)` 等签名全部变化，同时 `DefaultedList` → `NonNullList`。
3. `function/ClassWhimsyIdea/Effect/WI_EffectRadioactive.java` 与 `WI_EffectBioToxicity.java`、`RDT_EffectFireImbue/PoisonImbue` —— 使用 `EntityAttributes.GENERIC_MAX_HEALTH`（1.21.2 起改名 `MAX_HEALTH`）、基于 `UUID` 的 `EntityAttributeModifier`（1.21 起改为 `Identifier` 作 id）、`applyUpdateEffect` 签名变化。
4. `screen/ClassDEV/**`（`DEV_SimpleWorker_SH/_S`、`DEV_ScreenRenderInit`）—— `ExtendedScreenHandlerType<>(ctor)` 的构造方式、`HandledScreens.register`、`DrawContext` 渲染在 1.21+ 多次变动；26.2 又把 GUI 相关方法挪到 `Gui`/`Hud`。
5. `mixin/ClassBlockHeadsReborn/BHR_Compost4CropMixin.java` —— 注入的是 `CropBlock.canPlantOnTop` 与 `CropBlock.getAvailableMoisture`（**Yarn 名称 + 方法签名**双重依赖），`getAvailableMoisture` 曾因返回值类型与访问修饰调整而失效。
6. `function/ClassDEV/Render/DEV_Overlay*.java` + `item/ClassWhimsyIdea/WI_ShaderDevRed.java` —— 依赖 `GameRenderer.setBlockOutlineEnabled` 与后处理着色器，属渲染管线范畴。

### 6.1.1 网络可用性实测（2026-10-06，含一次重要更正）

**第一轮（错误结论）**：在 Windows PowerShell 5.1 中对各仓库做 `HEAD` 请求，全部失败（`基础连接已经关闭`）。当时据此判断"沙箱内无对外 HTTPS 能力"——**这个结论是错的**，已在第二轮推翻。

**第二轮（定位到真正原因）**：逐层排查后的完整证据链：

| 探测 | 结果 | 含义 |
| --- | --- | --- |
| DNS `Resolve-DnsName maven.fabricmc.net` | ✅ 解析到 Cloudflare IP | DNS 正常 |
| 原始 TCP 连接 `104.21.33.240:443` / `:80` | ✅ `True` | **TCP 出网正常** |
| 强制 TLS 1.2 后 `Invoke-WebRequest` | ❌ 仍失败 | 不是 TLS 版本协商问题 |
| `curl.exe https://maven.fabricmc.net/` | ❌ `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030E) 安全包没有可用的凭证` | **根因**：受限令牌拿不到本机 Windows TLS 凭据 |
| 本机代理配置 | `HKCU\...\Internet Settings`：`ProxyServer=127.0.0.1:7897` 但 `ProxyEnable=0`，且该端口未监听 | 代理未启用，不是代理问题 |
| **Java（JBR 25.0.4）发送 HTTPS 请求** | ✅ `maven.fabricmc.net` / `services.gradle.org` / `meta.fabricmc.net` / `repo1.maven.org` 全部 **HTTP 200** | **Java 走自带 JSSE + cacerts，不依赖 Windows schannel → 沙箱内可用** |
| 不受限运行时 `curl.exe` | ✅ 三个仓库全部 **HTTP 200** | 机器本身网络正常 |

**结论**：机器网络正常；**只有使用 Windows 原生 TLS（schannel）的程序**（PowerShell 5.1 的 `Invoke-WebRequest`、`curl.exe`）在沙箱内失败。**Gradle/JVM 使用 Java 自己的 TLS 栈，因此在沙箱内可以联网**。

⚠️ **但仍有残余障碍**（实测）：Gradle wrapper 用 `HttpURLConnection` 请求 `services.gradle.org` 时，**跟随重定向到 CDN 的那一次握手会被中断**（`SSLHandshakeException: Remote host terminated the handshake`）。同一 URL 用 `java.net.http.HttpClient` 却可以正常下载（见 §6.2 的处理方式）。

**"没有网络所以不能构建"的判断作废**，修订结论见 §6.2。

### 6.1.2 文件写入路径的实测边界

沙箱对不同子目录的写权限**并不一致**（`workspace-write` 模式下实测）：

| 操作 | 结果 |
| --- | --- |
| 在**工作区根**创建目录并写文件（含 `a/b/c` 多层嵌套） | ✅ 允许 |
| 在 `tmp\` 下创建子目录 | ❌ `PermissionDenied`（对路径的访问被拒绝） |
| 在 `doc\agent\deepseek\` 下创建子目录 | ❌ 同上 |
| 子进程 `git clone` 到 `tmp\...`（需创建目录树） | ❌ `could not create work tree dir: Permission denied` |
| 通过智能体自身的文件工具（read/write/edit）写上述位置 | ✅ 允许 |

→ **实践建议**：需要**子进程**（Gradle、git、编译器）大量创建目录/文件的临时工作，放在**工作区根**下的目录里（如 `toolchain-check/`），不要放在 `tmp/`、`doc/` 这类子目录里；智能体自身的文件工具不受此限制。

### 6.1.3 沙箱 ACL 故障与修复记录

工作区一度**完全不可写**：DSH 在切换到 `workspace-write` 时无法为工作区授权，报 `SetNamedSecurityInfoW failed (Win32 5): grantWrite(...)`，随后连只读命令也全部失败。
修复方式：运行 DSH 自带的 Windows 权限诊断脚本（一次不受限运行），它在工作区根目录为当前用户补上"完全控制"权限，并保留了备份与撤回脚本：

- 报告：`C:\Personal\Project\IntellijIDEA\MinecraftMod\dsh-acl-recovery\acl-report-8c7581ba0aca4e55b7279ab30d822fd8.jsonl`
- 备份/撤回脚本：同目录下 `acl-backup-454cf6ca58ff4d8385167f05533ea3be.json` 及其 `.ps1`
- 结果：`GRANTED`、`verification: verified`，`writeOwner` 由 `false` → `true`；修复后命令恢复正常

> 该目录位于**工作区之外**（与项目同级），是脚本默认要求的持久化位置，未纳入版本控制。
