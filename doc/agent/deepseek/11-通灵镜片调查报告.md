## 0. 结论先行（三个问题的直接回答）

| 问题 | 回答 | 一句话依据 |
| --- | --- | --- |
| **必须写成方块实体吗？** | **不必须，而且不建议** | 镜片没有"每方块状态"：它要广播的东西时刻可以由「世界状态（镜片坐标 / 下方信标）+ 信标自身状态」推导出来；周期性回调可以用**计划刻**（`scheduleTick` 自重排 80 tick）拿到，不依赖方块实体 |

## 2. 为什么不需要方块实体

### 2.1 方块实体能提供的四件事，方块侧都有等价物

| 方块实体能给 | 不用方块实体时用什么 | 证据 |
| --- | --- | --- |
| 每 tick / 每 80 tick 的**逐方块**回调 | **计划刻**：`level.scheduleTick(pos, this, 80)`，在 `tick(state, level, pos, random)` 里再排一次；计划刻**随区块存档保存**（`block_ticks`），重进世界后随区块加载而恢复 | `SerializableChunkData.java:104-105,136-138,484-485`；`ScheduledTickAccess.scheduleTick(BlockPos, Block, int)` |
| 逐方块的**状态持久化** | 不需要：镜片没有自己的状态（见 2.2）。全局索引的持久化是另一件事（§4.10，可选） | — |
| 被移除时的 `setRemoved()` 钩子 | `affectNeighborsAfterRemoval(state, ServerLevel, pos, movedByPiston)`（26.2 里取代了旧的 `onRemove`） | `BlockBehaviour.java:177`，调用点 `ServerLevel.java:864` |
| 区块加载后自动"醒过来" | 计划刻随区块一起恢复（同上），加载后最近一拍就会自报 | 同上 |

### 2.2 镜片没有"每方块状态"

它要上报的内容是：

```
(镜片坐标, 维度)  ← 由 pos + level.dimension() 得到
(信标效果, 等级)  ← 由 pos.below() 的 BeaconBlockEntity 现场读出
```

三个量**全都不需要在镜片里存**。反过来，如果给镜片加方块实体，方块实体里也只会写一层"转发"，而真正的索引仍然是全局的 —— 方块实体解决不了"跨维度索引"这个真问题。

### 2.3 方块实体的额外成本（本项目口径）

- 要登记 `BlockEntityType`（当前 `ModRegister` 只有 `BLOCK` / `ITEM` 两条注册入口，没有 BE 注册封装）；
- 方块要改继承 `BaseEntityBlock`（范式层 6 的"家族声明"会变），并覆写 `newBlockEntity` / `getTicker`；
- `doc/wiki/example/blockv1.md` §8 TODO 第 2 条正好记着「`BaseEntityBlock` 的 codec 26.2 是否已提供」还是**待核实项** —— 现在这个方块没必要去踩它。

### 2.4 结论

**不写方块实体。** 方块类里只保留"放置 / 拆除 / 邻居变化 / 计划刻"四个覆写点；全局索引与 80 tick 驱动放进独立服务类（符合范式 §7 第 9 条"同一条规则只有一份实现"）。

| --- | --- | --- | --- |

## 4. 26.2 API 事实（逐条实测）

### 4.1 信标时钟与效果结算（原版）

`BeaconBlockEntity.tick(Level, BlockPos, BlockState, BeaconBlockEntity)`（第 119 行起）的结算片段：

```java
int previousLevels = entity.levels;
if (level.getGameTime() % 80L == 0L) {                 // ← 信标时钟：80 tick = 4 秒
    if (!entity.beamSections.isEmpty()) {
        entity.levels = updateBase(level, x, y, z);    // 数金字塔：1~4 级
    }
    if (entity.levels > 0 && !entity.beamSections.isEmpty()) {
        applyEffects(level, pos, entity.levels, entity.primaryPower, entity.secondaryPower);
    }
}
```

`applyEffects`（第 257 行）：

```java
double range = levels * 10 + 10;
int baseAmp = 0;
if (levels >= 4 && Objects.equals(primaryPower, secondaryPower)) baseAmp = 1;
int durationTicks = (9 + levels * 2) * 20;             // 9~17 秒：4 级正好 17 秒
...
player.addEffect(new MobEffectInstance(primaryPower, durationTicks, baseAmp, true, true));
if (levels >= 4 && !Objects.equals(primaryPower, secondaryPower) && secondaryPower != null) {
    player.addEffect(new MobEffectInstance(secondaryPower, durationTicks, 0, true, true));
}
```

由此确定三件事：
1. 节拍判据就是 `level.getGameTime() % 80 == 0`；
2. 效果等级（amplifier）= `(levels>=4 && primary==secondary) ? 1 : 0`，**与主效果所选效果的"需求等级"无关**（原版不校验、只校验菜单选择；降级后的信标会继续发旧效果）；
3. 用户要的"固定 17 秒"= **340 tick**（4 级信标 `(9+4*2)*20 = 340`，正好吻合）。

另：26.2 的**信标可选项**是 `BEACON_EFFECTS`（public static，第 56-61 行）：速度/急迫、抗性/跳跃、力量、生命恢复。

### 4.2 读信标状态：私有字段 + 一条公开通道

`BeaconBlockEntity` 的字段（第 73-76 行）：

```java
private int levels;
private int beamSections...
private @Nullable Holder<MobEffect> primaryPower;
private @Nullable Holder<MobEffect> secondaryPower;
```

**没有任何 public getter**（`jarquery` 全量方法表里没有 `getLevels` / `getPrimaryPower`）。可用的公开通道有三条：

1. **NBT 快照**（推荐）：`BlockEntity.saveWithoutMetadata(HolderLookup.Provider)` / `saveCustomOnly(...)` / `getUpdateTag(...)`，三者都会走 `saveAdditional`，而 `BeaconBlockEntity.saveAdditional`（第 321-328 行）写的是：
   ```java
   storeEffect(output, "primary_effect", this.primaryPower);   // 效果 id 字符串
   storeEffect(output, "secondary_effect", this.secondaryPower);
   output.putInt("Levels", this.levels);                       // 金字塔等级
   ```
   读法（与 `BeaconBlockEntity.loadEffect` 第 309 行同一条路）：
   ```java
   CompoundTag tag = beacon.saveWithoutMetadata(level.registryAccess());
   int levels = tag.getIntOr("Levels", 0);
   TagValueInput in = TagValueInput.create(ProblemReporter.DISCARDING, level.registryAccess(), tag);
   Optional<Holder<MobEffect>> primary = in.read("primary_effect",
           BuiltInRegistries.MOB_EFFECT.holderByNameCodec());
   ```
   （`RegistryAccess extends HolderLookup.Provider`，已核实；`TagValueInput.create(ProblemReporter, Provider, CompoundTag)` 已核实。）
2. **`getBeamSections()`**（public，第 291 行）：`levels == 0` 时返回空表，否则返回光束分段 —— 可以当"光束是否被遮挡"的公开信号。
3. **`@Accessor` Mixin**：直接取三个私有字段。能用，但把功能抬到第 5 级，且**解决不了下面的时序陷阱**。

### 4.3 ⚠️ 时序陷阱：刚加载的区块里 `Levels` 会是 0

- `loadAdditional`（第 313-319 行）**不读 `Levels`** —— 只读两个效果和名字；
- `levels` 只在 80 tick 边界被 `updateBase` 赋值，且**只有光束分段非空时**才会算（第 166 行）；
- 光束扫描是逐 tick 推进的（`BLOCKS_CHECK_PER_TICK = 10`），而 `beamSections = checkingBeamSections` 的赋值发生在同 tick 的 **80 tick 判定之后**（第 176-179 行）。

所以：**区块刚加载 / 镜子所在区块刚被重新加载时，信标可能连续若干 tick（最多 4 秒）`levels == 0`，但它的金字塔其实是好的。**
如果校验规则写成"`Levels == 0` 就删记录"，那么每次区块加载、每次服务器重启后，都可能把一条本来有效的记录误删 —— 而记录一旦删掉，镜片不会自己回来（它只在被放置 / 自己那一拍上报时才写）。这是本功能最容易踩的坑。

**对策（已采纳，见 §7 第 3 条）**：不信 `Levels`，由镜片侧**自己按原版规则数金字塔**（`BlockTags.BEACON_BASE_BLOCKS`，第 195-221 行就是全部规则：第 n 层 `y-n`、`x±n`、`z±n` 全是信标基座方块，n=1..4）。数出来的等级没有时序问题，且与信标自己的 `updateBase` 完全同源。
代价：每个镜片每 4 秒 9+25+49+81 = 164 次 `getBlockState`；先用 `level.hasChunksAt(pos.offset(-4,-4,-4), pos.offset(4,0,4))` 兜底，区块不全就"无法校验 → 保留"。
D3 确认要"光束被挡也算失效"后，回退扫描还会多一段"从信标上方扫到 WORLD_SURFACE 找不透明方块"（§7 第 3 条 ②-b）——**只在 `getBeamSections()` 为空的拍子才跑**，平时只花一次 `getBeamSections()`。

### 4.4 区块是否加载（不触发加载！）

- `LevelReader.hasChunkAt(BlockPos)` / `hasChunkAt(int,int)` —— 纯查询；
- `Level.getChunkSource().getChunkNow(x,z)` —— 未加载返回 `null`（`ChunkSource.getChunkNow`）；
- ⚠️ 不要用 `level.getChunk(x,z)` / `getBlockState` 去"查"未加载区块：那会**同步加载**区块。

### 4.5 施加效果（17 秒 = 340 tick）

`LivingEntity.addEffect(MobEffectInstance)`（final 方法，已核实）；构造器 `MobEffectInstance(Holder<MobEffect>, int duration, int amplifier, boolean ambient, boolean visible)`（5 参，已核实）：

```java
player.addEffect(new MobEffectInstance(holder, 340, amp, true, true));
```

`addEffect` 自带合并：玩家已有更强的同效果实例时不会被降级，重复施加只是续时长 —— 多个镜片给同一效果不会有副作用。

### 4.6 维度与玩家

- 维度键：`Level.dimension()` → `ResourceKey<Level>`（`ServerLevel` 继承）；
- 该维度玩家：`ServerLevel.players()`（`List<ServerPlayer>`）；
- 全维度遍历：`MinecraftServer.getAllLevels()` → `Iterable<ServerLevel>`（`MinecraftServer.overworld()` 也可取主世界）。

### 4.7 全局拍子（Fabric 事件，第 4 级）

`fabric-lifecycle-events-v1`（本项目 Fabric API `0.161.0+26.2` 内）：

```java
ServerTickEvents.END_LEVEL_TICK  // Event<EndLevelTick>：每次 ServerLevel.tick 末尾，参数就是 ServerLevel
ServerTickEvents.END_SERVER_TICK // 整个服务器 tick 末尾
ServerLevelEvents.LOAD / UNLOAD
ServerChunkEvents.CHUNK_LOAD / CHUNK_UNLOAD
```

**对齐证明**：`ServerLevel.tick` 里先 `tickTime()`（推进 `gameTime`，第 386 行）→ `blockTicks.tick(...)`（第 389-397 行）→ `chunkSource.tick(...)`（第 405 行，**方块实体在这里 tick**）。所以：

- 在 `END_LEVEL_TICK` 里判 `level.getGameTime() % 80 == 0`，与信标**同一 tick**，且此时信标刚结算完 —— 读到的是本拍的结果；
- 镜片自己的计划刻跑在 `blockTicks` 阶段（**早于**信标方块实体），所以镜片自报用的是上一拍的信标状态。**建议：镜片自报只负责"写/改记录"，施加效果统一放在 `END_LEVEL_TICK`。**（差一拍对 4 秒级的广播没有实际影响。）

### 4.8 放置 / 移除 / 邻居通知的真实调用点

| 钩子 | 26.2 签名 | 调用点（实测） | 用途 |
| --- | --- | --- | --- |
| 放置 | `protected void onPlace(BlockState, Level, BlockPos, BlockState oldState, boolean movedByPiston)` | `LevelChunk.setBlockState` 第 320-322 行（仅服务端、`flags & 512 == 0`） | 首次上报（`/setblock` 也能覆盖，`setPlacedBy` 只覆盖玩家放置） |
| 移除 | `protected void affectNeighborsAfterRemoval(BlockState, ServerLevel, BlockPos, boolean movedByPiston)` | `ServerLevel.updateNeighboursOnBlockSet` 第 864 行 | 拆除 → 上报失效、删记录 |
| 邻居变化 | `protected void neighborChanged(BlockState, Level, BlockPos, Block, @Nullable Orientation, boolean)` | 由 `ServerLevel.updateNeighborsAt` 派发 | 正下方方块被换掉时立即修正（信标金字塔变化**不会**通知到镜片） |
| 形状 | `protected VoxelShape getShape(BlockState, BlockGetter, BlockPos, CollisionContext)` | 默认 `Shapes.block()`；`getCollisionShape` 默认等于 `hasCollision ? state.getShape(...) : Shapes.empty()`（第 327-333 行） | 只覆写 `getShape` 就同时得到薄碰撞箱，不必再写 `getCollisionShape` |

### 4.9 计划刻（无方块实体的周期回调）

```java
// 放置时排第一拍
level.scheduleTick(pos, this, 80);
// 在 tick(...) 里自重排
level.scheduleTick(pos, this, 80);
```

- `ScheduledTickAccess.scheduleTick(BlockPos, Block, int)`（已核实；`Level` 实现它）；
- 计划刻**按区块存档**：`SerializableChunkData` 的 `block_ticks`（第 104-105、136-138、484-485 行）→ 重进世界后随区块加载恢复；
- 只在区块**正在 tick** 时执行；区块卸载期间不执行、也不丢失。

### 4.10 全局索引要不要落盘（可选项）

- 内存版：服务端单例，服务器停就没了；镜片靠计划刻在区块加载后 4 秒内**自我重建**。
- 落盘版：`SavedData` + `SavedDataType(id, Supplier, Codec, DataFixTypes)`，存到 `level.getDataStorage().computeIfAbsent(dataType)`（`SavedDataStorage` 已核实）。需要给"维度 → 效果 → 等级 → 坐标表"写一套 codec。
- **两种都改变不了的一条**：区块没加载时镜片不 tick，落盘版才能真正做到"重启后未加载区块里的镜片继续广播"。

### 4.11 原版"有效性"其实是三件事、三种节拍（回答"是不是每个信标时钟才算一次"）

| 算的是什么 | 什么时候算 | 代码位置 |
| --- | --- | --- |
| **光束有没有被挡**（`beamSections`） | **每 tick**，增量扫描：一轮 10 块（`BLOCKS_CHECK_PER_TICK`），从信标自身那一格一直扫到 `level.getHeight(WORLD_SURFACE, x, z)`；扫到 `lightDampening >= 15 && !BEDROCK` 就 `checkingBeamSections.clear()`；一轮结束时 `beamSections = checkingBeamSections` | `BeaconBlockEntity.java:124-162`、`:176-179` |
| **金字塔数几层**（`updateBase`） | **只在 80 tick 边界**，而且**只在 `beamSections` 非空时**才算 | 同上 `:165-169`、`:195-221` |
| **施加效果**（`applyEffects`） | **只在 80 tick 边界**，且要 `levels > 0 && !beamSections.isEmpty()` | 同上 `:170-174` |

所以：
- "数金字塔"确实是信标时钟（80 tick）一次，但**光束遮挡是每 tick 持续扫的**，两者不是同一拍；
- 光束被挡时 `levels` **不再更新**（停在旧值），这正是"只看 `Levels` 判有效性"会错的原因（§4.3）；
- **镜片放在信标正上方不会被当成遮挡**：扫描到信标那一格时已经建好第一个光束段（`BeaconBlock` 实现 `BeaconBeamBlock`），随后扫到镜片走"延伸光束"分支；判定遮挡的是 `state.getLightDampening() >= 15`，而薄玻璃镜片算出来是 0 或 1（`BlockBehaviour.java:303-308`，`solidRender = isShapeFullBlock(occlusionShape)`，`:521/:666`）。**前提是这个方块别写成实心/不透明**（父级玻璃 + `getShape` 薄层就满足）。

### 4.12 光束状态**不**写进方块数据

- `saveAdditional` 只写 `primary_effect` / `secondary_effect` / `Levels` / `CustomName` / lock（`:321-328`）；
- `loadAdditional` **只读效果、名字、锁**，**不读 `Levels`**（`:313-319`）—— `Levels` 是"只写不读"的存档字段；
- `beamSections` / `checkingBeamSections` / `lastCheckY` 都是**纯运行时字段**，不进 NBT、不进网络包；
- 客户端的光束是**客户端自己算的**：`BeaconRenderer` 读的是客户端方块实体的 `getBeamSections()`（`BeaconRenderer.java:49`），而客户端每个 tick 都会跑方块实体 tick（`Minecraft.java:1913` → `Level.tickBlockEntities()`），所以客户端用自己那份世界重新算，不靠服务端同步"是否发光"。

**结论**：原版信标没有任何"我在发光 / 我有效"的持久标记，有效性永远是现场重算出来的。这也说明镜片"搬运下方信标状态"只能靠**现场读**（§4.2 的 NBT 快照 + §7 自己的判定），不能指望读到一个已存好的标志位。

## 5. 数据结构（按用户要求逐层落地）

用户要求：**以维度为根 → 效果数组 → 每个等级一个数组 → 里面是所有对应坐标**；坐标列在效果后面当数组本身就是为了让"多重相同效果"不打架。**D6 已确认：不去重，施加按节点做一次。**

```java
// 全局索引（服务端单例，全部在服务端线程访问）
final class RDT_SpectreLensIndex {
    // 维度 → 效果 → 等级(1..2) → 坐标集合
    Map<ResourceKey<Level>, Map<ResourceKey<MobEffect>, Map<Integer, Set<BlockPos>>>> index;
    // 反查：拆镜片 / 邻居变化时按坐标 O(1) 找到它挂在哪些 (效果, 等级) 上
    Map<ResourceKey<Level>, Map<BlockPos, Set<RecordKey>>> byPos;
}
```

要点：

1. **效果键用 `ResourceKey<MobEffect>`，不要用 `Holder`**：`Holder.Reference` 没有覆写 `equals/hashCode`（`jarquery` 方法表已核实），跨来源的 Holder 不保证同一实例；`ResourceKey` 是 interned 的（`ResourceKey.VALUES`），可以安全当键。施加时：`BuiltInRegistries.MOB_EFFECT.get(key.identifier()).map(BuiltInRegistries.MOB_EFFECT::wrapAsHolder)`。
2. **等级 = amplifier + 1（1 或 2）**（D1 已确认），原因见 §4.1：原版的强度只有两档；"信标金字塔等级 1~4"是另一个量，不进记录。
3. **坐标数组就是去重器**（D6 已确认）：多个镜片给同一 (维度, 效果, 等级) 时，坐标都进同一个 `Set<BlockPos>`；**施加时按 (维度, 效果, 等级) 节点做一次**，不是按坐标做 N 次。坐标只用于校验与删除。
4. 一个镜片可能同时挂 **2 条**记录（4 级信标主/副效果不同时）；也可能只挂 1 条 —— 两条落在不同的 (效果, 等级) 节点里。
5. **空数组即删除信号**：删坐标后集合为空 → 删掉该 `(效果, 等级)` 节点；效果节点空了 → 删掉该效果；维度节点空了 → 删掉该维度。这样"记录是否存在"永远等价于"对应数组非空"。
6. 维度用 `ResourceKey<Level>`（`Level.OVERWORLD` / `Level.NETHER` / `Level.END` / 自定义维度）。

## 6. 生命周期时刻表

| 时刻 | 触发点 | 该做什么 |
| --- | --- | --- |
| 镜片被放置 | `onPlace`（服务端） | 读正下方信标 → 有效则写记录；排第一拍计划刻（80） |
| 每 80 tick（镜片自己） | 计划刻 `tick(...)` | 自重排 80 tick；重算当前应记的 (效果, 等级) 集合 → 与旧记录不一致就"删旧 + 写新"（D2）；信标失效就只删 |
| 每 80 tick（全局） | `ServerTickEvents.END_LEVEL_TICK`（`gameTime % 80 == 0`） | ① 校验全部记录（§7）② 按 (维度, 效果, 等级) 节点各给该维度所有玩家施放一次（340 tick） |
| 镜片被拆除 | `affectNeighborsAfterRemoval` | 按坐标删掉它的全部记录 |
| 正下方方块变化 | `neighborChanged` | 立即重算：有效 → 改记录；失效 → 删记录 |
| 区块卸载 | `ServerChunkEvents.CHUNK_UNLOAD`（可选） | **什么都不做** —— 记录保留（用户明确要求） |
| 区块重新加载 | 计划刻随区块恢复 | 最多 4 秒后镜片自己会把记录修正回来 |
| 服务器重启 | 内存索引清空 | 不落盘时：区块加载后 4 秒内自动重建；落盘时：直接读回（§4.10） |

## 7. 校验规则（逐条对齐用户规格 R2~R6，含 D3 的"光束"判定）

对每条记录 `(维度 D, 效果 E, 等级 L, 坐标 P)`：

1. `P` 所在区块没加载（`!level.hasChunkAt(P)`）→ **保留**（用户明确："查询失败也算有效"）。
2. 区块已加载，但 `level.getBlockState(P)` 不是通灵镜片 → **删除**。
3. 是镜片，但 `P.below()` 不是信标 / 信标"有效结算"不成立 → **删除**（信标"失去效果"）。
   这里的"有效结算"= 原版 `tick` 里 `levels > 0 && !beamSections.isEmpty() && primaryPower != null`，也就是：
   - **金字塔有效**（自己数，1~4 级；规则见 §4.3 末段，别读 NBT 的 `Levels`）；
   - **光束没被挡**（D3：严格镜像原版）；
   - **已选主效果存在**（NBT `primary_effect`）。
   判定顺序（避开 §4.3 的竞态）：
   ```
   ① getBeamSections() 非空  → 光束 OK（且蕴含 levels>0），沿用自己数的金字塔等级
   ② getBeamSections() 为空  → 用确定性回退扫描再判一次：
        a. 数金字塔：0 级 → 失效
        b. 从 y+1 扫到 level.getHeight(WORLD_SURFACE, x, z)：
           若存在 state.getLightDampening() >= 15 && !state.is(Blocks.BEDROCK) → 光束被挡 → 失效
        c. 都通过 → 保留（这就是"区块刚加载、信标还没算完"的情况，不能删）
   ```
   > 为什么不用 `getBeamSections()` 单判：它内部 `levels == 0 ? empty : beamSections`（第 291-293 行），
   > 而刚加载的区块 `levels` 还是 0（§4.3），会把好信标误判成"失效"。
4. 信标当前应记的集合里**没有** `(E, L)` → **删除**（信标"改变效果"）。
5. 全部通过 → 保留；镜片那一拍顺手把集合对齐（D2：删旧 + 写新）。

> 建议把 1~4 做成"校验"、把"写回"留给镜片那一拍（§6），这样"删除"与"新增"各只有一个入口，不会互相打架。
> 回退扫描（3-b）只在"快路径为空"时跑，绝大多数拍子只花一次 `getBeamSections()`。
