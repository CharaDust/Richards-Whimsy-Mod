# 03 · 「直接重制所有功能」方案可行性评价

- 评价人：DeepSeek 智能体（deepseek-flash）· 2026-10-06
- **评价范围（严格限定）**：仅依据
  1. `doc/wiki/` 中已写的 wiki 规格（当前 10 份：`ClassRandomThings` 7 份 + `ClassWhimsyIdea` 3 份）；
  2. `src/main/java/com/rcdmake/whimsy/block/ClassRandomThings/` 与 `ClassWhimsyIdea/` 下的实现代码（14 个文件，已读 13 个，`BlockEntity/RDT_BlockBreaker.java` 未读）。
- **不做的事**：不补全、不修改任何功能文档；不设计迁移步骤；不动代码。

---

## 1. 结论

**「直接重制」在本评价覆盖的这两个包内是可行的，而且大概率比"移植"更省事；但它不能作为"所有功能"的统一策略。**

原因一句话：这两个包里的"功能"绝大部分是**声明式配置**（构造参数 + 2~4 个方法覆写），移植一个 40 行的配置型方块和重写它，工作量几乎相同；而 wiki 已经把规格写成了与实现无关的形式，正好可以当重制的验收依据。

但**重制的风险不在这些方块，而在于 wiki 尚未覆盖、且逻辑真正存在于代码里的那部分**（方块实体、容器界面、配方、物品 NBT/组件、状态效果、渲染管线与数据生成）。对那些部分，"重制"意味着在没有规格的情况下凭记忆重写，这才是丢行为的所在。

---

## 2. 依据 A：wiki 作为"重制规格"的质量

**优点（对重制有利）**

| 特征 | 说明 |
| --- | --- |
| 与实现解耦 | 每份 wiki 用「特点简介 + 构造属性表 + 渲染 + 改写方法 + 事件 + 方块状态」描述**行为与参数**，不引用类名/方法名 → 天然可用于任意版本重写 |
| 参数被显式记录 | 例如硬度 0.3 / 爆炸抗性 15.533（"TNT 恰好炸穿 1 层"）、地图颜色 `PALE_YELLOW`、声音组 `SCAFFOLDING`/`SNOW`/`MUD`、亮度、`FALSE`/`默认`/`父级` 三态 |
| 标注了"未实现" | 鲁米诺纯色渲染、通灵原木减速、固化水后期上色、固化水"仅推动" —— 这些是**已知缺口**，重制时可以明确决策"做/不做"，而不是靠猜 |
| 标注了"待定" | 地图颜色 `父级*`、引燃/烧毁几率 `父级*`、`硬度 100 随意填写` —— 重制时需要先补决策 |

**缺口（对重制不利）**

- **覆盖不全**：wiki 现有 10 份方块规格，而项目注册了 **29 个方块、37 个物品、4 个状态效果、5 个物品栏、2 个方块实体、1 个容器界面、1 个配方类型**。仅就方块而言，覆盖率约 10/29。
- **不含获取方式**：全部 10 份的「获取方式」都是"无"，即掉落/合成/可获得性尚未定义 → 重制后"能拿到"这件事没有规格可依。
- **不含跨方块机制**：这些方块与物品栏、标签、数据生成、客户端渲染初始化的关系不在单方块规格里。

## 4. 风险清单（重制路线下必须正视的四条）

1. **规格缺口 = 无声丢失**。wiki 未覆盖的部分（尤其方块实体/配方/界面/NBT/状态效果），其行为只存在于代码中。重制时若不同时建立"从代码反推规格"的步骤，就是凭记忆重写。
2. **错误不可归因**。重制把"学 26.2 新 API"和"重写功能"这两件事叠在同一时刻：每个自定义方块在 1.20.5+ 都新增了 codec 提供义务，玻璃系的碰撞箱判定、糖块的"踩/击碎"、垫脚方块的计划刻，都需要在新 API 下重新找对应方法。一旦出错，无法判断是"写错了功能"还是"用错了新 API"。
3. **wiki 自身的待定项会阻塞重制**。`父级*`（地图颜色/引燃几率）、"随意填写"（硬度 100）、"未实现"若要补做，都需要先做设计决策。
4. **26.2 目标实现路径未知的功能**。鲁米诺方块"忽略任何修改因素渲染为纯色"依赖 Fabric 的 `emissiveLighting`（该 API 在新版是否保留未核实）；固化水"和原版水同原理的后期上色"依赖 `Biome#getWaterColor` 与颜色注册（`ColorProviderRegistry` → `BlockColorRegistry`）。这两项**没有确定的新版实现路径**，属于真正的技术不确定性。

## 5. 建议的边界划分（评价结论，非执行计划）

| 范围 | 「直接重制」是否合适 | 理由 |
| --- | --- | --- |
| 上述两个包内的 10 个方块 | ✅ 合适 | 声明式为主，wiki 已覆盖，重制成本≈移植成本，且能顺带清掉历史包袱（死导入、错误的 `super` 调用、注释掉的代码） |
| 客户端渲染接线（2 个 ClientRenderInit） | ✅ 合适且必要 | 旧 API 已删除，只能重写；按 wiki 的透明描述可验证 |
| 方块实体 / 容器界面 / 配方 / 物品组件 / 状态效果 / 数据生成 / Overlay 渲染 | ⚠️ 需先有规格 | 逻辑集中于这些文件，wiki 目前无对应规格；"重制"在此等于高风险重写 |
| 获取方式（掉落表/配方/可获得性） | ⚠️ 规格为空 | 10 份 wiki 全为"无"，重制后无法验收"能拿到" |

**一句话总结**：把「重制」当作**这两个包的默认做法**是划算的；把它当作**全局策略**则会在 wiki 尚未覆盖的地方产生不可验证的重写。可行性不取决于"模组功能是否简易"，而取决于**目标功能是否已有一份与实现无关的规格**——已有规格的，重制优于移植；没有规格的，先有规格再谈重制。
