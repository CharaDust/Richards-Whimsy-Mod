# 13 动物取食容器方块 —— 范式定级调查

> 调查对象：方块实体存物品（木桶/箱级）+ 动物有时主动过来、从箱中取食、效果等同被玩家喂食。
> 结论口径：`doc/wiki/example/blockv1.md` 的 **分层 0–12（+C/M）** 与 **能力阶梯 0–5**。
> 证据来源：本机 Loom 缓存 26.2 deobf jar 反编译（`Toolchain-check/vineflower.jar`）、Fabric API 0.161.0+26.2 内含子 jar、项目现有源码。
> 调查日期：2026-10（对应 MC 26.2 / Fabric loader 0.19.5 / loom 1.18.2）

---

## 0. 先说一个前提：这三件事不全在 V1 的管辖范围内

`blockv1.md` §1 写明适用对象是「本模组**所有方块类**」，层表 0–12 描述的是**方块本体**的生命周期。
本需求的四个部分里，只有第 ① 部分落在 V1 里：

| 部分 | 是否 V1 覆盖 | 说明 |
| --- | --- | --- |
| ① 容器方块本体（`EntityBlock`、`newBlockEntity`、交互开界面） | 是 | 层 6 / 8 / 9 / 12 |
| ② 方块实体（槽位、存档、掉落、同步） | **否** | V1 无对应层；§8 TODO #2 只留了一句「BaseEntityBlock codec 待核实」 |
| ③ 界面（菜单 + 屏幕） | **否** | 另见 `Misc/界面与容器.md` |
| ④ 实体 AI（寻块、到站、被喂食） | **否** | 与方块无关，属实体域 |

所以下面的定级表里，②③④ 的「层」一列我标 `—`（V1 不覆盖），只给阶梯级（阶梯是**手段**分级，跨域仍然成立）。

## 2. ② 存储本体的三条路，只有两条成立（实测）

| 候选父类 | 能否继承 | 证据 |
| --- | --- | --- |
| `BarrelBlockEntity` | **不能** | 唯一构造器 `BarrelBlockEntity(BlockPos, BlockState)` 里写死 `super(BlockEntityTypes.BARREL, …)`（反编译 :28-30），`BARREL` 的 `validBlocks` 不含我们的方块 |
| `ChestBlockEntity` | **能** | 另有 `protected ChestBlockEntity(BlockEntityType<?>, BlockPos, BlockState)`（:33），正是为接管自定义类型留的口子 —— 与 `SignBlockEntity` 同一种设计 |
| `RandomizableContainerBlockEntity` | **能** | `protected (BlockEntityType<?>, BlockPos, BlockState)`（:24），白拿战利品表支持，但格数与开盖计数要自己写 |

**「木桶」这个隐喻在代码层面恰好是错的那一半**：木桶实体不可继承，箱子实体可继承。要木桶的手感（27 格、开盖动画）得走实体继承 + 自己接开盖器，或者干脆走 2' 自写路线。

告示牌踩过的坑在这里会**原样重演**，必须提前记住（`BHR_TreeSignFruit` 类注释 :40-50）：

1. 必须注册**自己的** `BlockEntityType`，并且在 `newBlockEntity` 里用**自己的类型**造实体，否则 `BlockEntityType.create` 判定不匹配 → **存档读取时内容悄悄丢失**（对应告示牌「字丢了」）；
2. `getTicker` 若继承父类的 `createTickerHelper(type, 父类型, …)`，自己的类型永远匹配不上 → 覆写指回自己的类型。

## 3. ④ 动物这一半

### 3.1 「有时过来」= `MoveToBlockGoal`，阶梯 0

26.2 里 `MoveToBlockGoal` 仍在（`net.minecraft.world.entity.ai.goal.MoveToBlockGoal`，反编译已核对）：

```java
public abstract class MoveToBlockGoal extends Goal {
	public MoveToBlockGoal(PathfinderMob mob, double speedModifier, int searchRange);
	public MoveToBlockGoal(PathfinderMob mob, double speedModifier, int searchRange, int verticalSearchRange);
	protected abstract boolean isValidTarget(LevelReader level, BlockPos pos);   // :128 唯一必须实现
	protected BlockPos getMoveToTarget();          // 可在旁边坐下/绕行时覆盖
	protected int nextStartTick(PathfinderMob mob); // 决定「有时」的频率
	protected boolean isReachedTarget();
}
```

白拿的东西：周围区块扫描（`findNearestBlock`，含 `mob.isWithinHome` 过滤）、寻路、到站判定、`nextStartTick` 的随机节流、`tryTicks` 超时放弃。`AgeableMob extends PathfinderMob`（反编译 :30），所以所有 `Animal` 都满足入参。

需要自己决定的两点：
- **扫描代价**：`findNearestBlock` 每次按 `(2*searchRange+1)² × verticalSearchRange` 逐个问 `isValidTarget`。`isValidTarget` 里必须先判方块类型、再 `getBlockEntity` 读槽位，否则几十只动物会把 tick 打满。
- **优先级**：以牛为例（`AbstractCow` :41-47）0 浮水 / 1 恐慌 / 2 繁殖 / 3 诱惑 / 4 跟幼 / 5 乱走。插在 3 之后（比「乱走」积极）还是 5 之后（比「乱走」消极）得选，影响「有时过来」的手感。

### 3.2 「挂进原版动物」= 阶梯 4，不是 5

`Mob#goalSelector` 是 `protected final`（`Mob.java:141`），跨包拿不到。两条路：

| 路线 | 级 | 代价 |
| --- | --- | --- |
| `ServerEntityEvents.ENTITY_LOAD`（`onLoad(Entity, ServerLevel)`）+ classtweaker 放开 `Mob.goalSelector` | **4** | 一条事件 + 一条 `accessible field`；运行时 `addGoal` 是原版支持的用法（`GoalSelector.addGoal` public，`:21`） |
| Mixin `Mob#registerGoals` TAIL | 5 | `registerGoals()` 在 `Mob` 构造器内被调用（`:166` 调 `:170`），各物种在自己构造器里先 `super.registerGoals()`（`AbstractCow:40-41`）—— 时机能覆盖，但要处理「非 Animal 过滤」与「重复添加」，且须三处登记 + `require = 0` + 游戏内验证 |

按 §3 铁律「能用上一级就不许用下一级」，选 **4**。这条路线在 V1 落地表里**没有先例**（表里标 4 的 `RDT_SpectreLens` 是跨类共享实现，不是事件回调），本需求会是第一个真正的第 4 级案例 —— 建议层 0 契约栏里把「为什么没用 Mixin」写清楚。

### 3.3 喂食效果：全 public API，零升级

核对过可见性（`Animal.java` / `AgeableMob.java` 反编译行号）：

| 要做的事 | 方法 | 可见性 |
| --- | --- | --- |
| 判定这食物它吃不吃 | `Animal#isFood(ItemStack)` :130 | public（各物种用 `ItemTags.*_FOOD` 实现） |
| 能不能进入求偶 | `Animal#canFallInLove()` :161 | public |
| 进入求偶（600 tick + 爱心粒子） | `Animal#setInLove(@Nullable Player)` :165 | public，**传 null 合法**，仍会 `broadcastEntityEvent(18)` |
| 幼崽加速成长 | `AgeableMob#ageUp(int seconds, boolean forced)` :122 | public |
| 加速量换算 | `AgeableMob#getSpeedUpSecondsWhenFeeding(int ticksUntilAdult)` :253 | public static |
| 吃东西音效 | `Animal#playEatingSound()` :158 | **protected** ← 唯一障碍；自己 `level.playSound(...)` 即可，不值得为它拓宽 |

**不推荐**的做法：`Animal#mobInteract(Player, InteractionHand)` 虽然是 public（:132），但它要么带一个 `Player` 实例、要么成年分支还要求 `ServerPlayer`（:136）。Fabric 没有内置 FakePlayer，自己实现 `Player` 抽象类只为调这一个方法，代价远大于直接复刻它的三步（扣物品 → 求偶/成长 → 音效）。

两个必须记住的行为细节：
- `Animal#aiStep` :69-73 每 tick 执行 `if (getAge() != 0) inLove = 0;` —— **幼崽永远不会进入求偶态**，喂幼崽只能走成长分支。
- `setInLove(null)` 不写 `loveCause`，所以繁殖时的 `ANIMALS_BRED` 统计与 `BRED_ANIMALS` 进度**不会**记到任何人头上。若希望「记在放置箱子的人名下」，得把那个 `ServerPlayer` 存进方块实体，并在繁殖时补账 —— 那已经超出「像被玩家喂食」，属新需求。

## 4. 范式缺口（本次调查顺带确认的）

1. **V1 只覆盖方块本体**：方块实体、容器、界面、实体 AI 四块都没有层表。本需求四占其三，要么新开一份 `blockentityv1.md`，要么在 V1 里加「层 BE」——后者会破坏「方块类的工艺说明书」这个定位，建议前者。
2. **§8 TODO #2 可以结案**：项目里 3 个 26.2 方块实体全走 `Block implements EntityBlock` + `newBlockEntity`，**没有一处覆写 `codec()`**。说明「BE 方块必须实现 codec」这个担心在 26.2 的这条路线下不存在。
3. **访问拓宽不在阶梯里**：classtweaker 的 `accessible` 已在用（`MenuType` 两条），但它不改行为、只放开可见性，介于第 3 级与第 5 级之间。阶梯 0–5 没有它的位置，是条文缺口 —— 本次第 5 项正好靠它把级别从 5 压到 4。
4. **第 4 级（事件/跨类通知）零先例**，§10.2 第 6 条「谁判定前四级真的无解」也还悬着。本次是第一个真实案例，适合作为 V2 的定级范本。

## 6. 两个候选方案定级对比（2026-10 追加）

前提（两方案共用）：`BHR_FeederChest`，`FACING` 按熔炉「面朝玩家放置」，无开盖动画/声音，动物**会主动寻路**到面朝方向前方一格。

### 6.0 两方案共用的开销

| 项 | 层 | 阶梯级 | 备注 |
| --- | --- | --- | --- |
| `FACING` 属性字段 + `createBlockStateDefinition` + `getStateForPlacement` | 层 3 + 层 8 | **2** | 熔炉原式：`setValue(FACING, context.getHorizontalDirection().getOpposite())`（`AbstractFurnaceBlock:50-51`） |
| 多状态 ⇒ blockstate / 模型**手写** | 资源 | — | 范式 §4 硬约束；furnace 式四面朝向 |
| 继承路线 | 层 6 | **0** | ⚠️ **不要**继承 `HorizontalDirectionalBlock`：它的 `codec()` 是抽象方法（反编译 :17），会强加层 7；走 `Block implements EntityBlock` 自声明 `FACING` 则 `Block.codec()` 已实现（`BHR_GemAmethyst:52` 记的就是这个坑） |
| 动物寻路到前方一格（`MoveToBlockGoal` 子类） | — | **0** | 只需 `isValidTarget(LevelReader, BlockPos)` |
| 把 goal 挂进原版动物 | — | **4** | `ServerEntityEvents.ENTITY_LOAD` + classtweaker 放开 `Mob.goalSelector` |

**共用上限 = 阶梯 4。** 只有当「动物主动寻路」这条需求被放弃时，上限才会掉下来（见 §6.3）。

### 6.1 方案 A：动物到站后向箱子请求

| 项 | 层 | 阶梯级 |
| --- | --- | --- |
| 在已有 Goal 的 `tick()` 里判 `isReachedTarget()` → 调 `be.tryFeedTo(animal)` | — | **0** |
| 箱内取物 → `animal.isFood(stack)` → 扣 1 → `setInLove(null)` / `ageUp(...)` | — | **0**（全 public API，见 §3.3） |
| 30 s 冷却 | — | **0，白拿**：`setInLove` = 600 tick = 30 s，`canFallInLove()` 自动挡住重复喂食 |

- 额外机制：**无**。喂食就是已有 Goal 的一个分支。
- 额外收益：`isValidTarget` 天然先问「这箱子里有没有**我**能吃的」，没食物就不会走过去；`goalSelector.tick()` 在 `Mob#serverAiStep()`（`Mob.java:710/729`），**只在服务端执行**，所以读方块实体没有双端副作用（§5 待实测 #4 对方案 A 自动消解）。
- 需要补的：幼崽没有 inLove 计时，重复喂食要自己加一次冷却（或接受幼崽一次吃到成年）。

### 6.2 方案 B：箱子轮询前方一格

| 项 | 层 | 阶梯级 |
| --- | --- | --- |
| 覆写 `EntityBlock#getTicker` 注册服务端 ticker | 层 8 | **2** |
| `level.getEntitiesOfClass(Animal.class, 前方 AABB)` 每 tick/每 N tick 扫描 | 层 8 | **2**（同一次覆写内） |
| 自己维护 `nextFeedTick`（30 s = 600 tick，`level.getGameTime()`） | 层 1 / 8 | **1~2** |
| 食物匹配：27 格 × 前方实体 × `isFood` 遍历 | — | **0**（逻辑量，不升级别） |

- 额外机制：**一条 ticker**（项目 `BHR_Campfire#getTicker` 有同型先例，等于可抄）。
- 代价：每个喂食箱每 tick 都在跑，即使周围没有动物；冷却要自己写；`Container` 侧还要暴露「哪一格能喂谁」的查询给方块。

### 6.3 结论

**按「动物会主动寻路」这个前提：方案 A 更低。**

- 喂食这一步 A = 0 级、B = 2 级；两者总上限都被「挂 goal」钉在 4 级，所以 B 是在同一上限上**多挂一层机制**，违反 §3 铁律「能用上一级就不许用下一级」。
- 你给 B 设计的「30 秒冷却」，在 A 里由原版求偶计时器免费提供（600 tick = 30 s），而且是**每只动物各自**的冷却 —— 比箱子侧全局冷却更符合「被玩家喂食」的语义。

**唯一能翻盘的走法**：放弃「主动寻路」，接受「动物自然游荡到箱前才吃」。那样 B 独立成立：

| | 上限 | 是否需要碰实体域 | 是否需要 classtweaker 放宽 |
| --- | --- | --- | --- |
| A | 4 | 需要（加 goal） | 需要（放开 `goalSelector`） |
| B（无 goal） | **2** | **不需要** | **不需要** |

即：**B 的 2 级只有在删掉「寻路」这条需求时才成立**；只要保留寻路，A 永远更省。若确实想要「箱子吸引动物过来」又不想碰实体域，没有第三条路 —— 从方块侧调 `mob.getNavigation().moveTo(...)` 会被动物自身的 MOVE-flag goal（乱走/恐慌）覆盖，属**看起来省一级、实际不成立**的假解法。

## 8. 落地记录（2026-11，方案 A 已实现）

### 8.1 实际采用的路线（与上面各节结论一致）

| 项 | 决策 | 对应级别 |
| --- | --- | --- |
| 方块本体 | `Block implements EntityBlock` + 自声明 `FACING`，**不继承** `HorizontalDirectionalBlock`（它 `codec()` 抽象） | 层 3/8，阶梯 2 |
| 存储 | 自写 `BlockEntity implements Container`（27 格），不继承 `BarrelBlockEntity`（构造器写死 `BlockEntityTypes.BARREL`） | 层 8/12，阶梯 2 + 3 |
| 界面 | `ChestMenu.threeRows(id, inv, container)` + `SimpleMenuProvider`，**零 MenuType、零 Screen、零客户端代码** | 阶梯 0~1 |
| 寻路 | `MoveToBlockGoal` 子类 | 阶梯 0 |
| 挂载 | `ServerEntityEvents.ENTITY_LOAD` + `classtweaker` 放开 `Mob.goalSelector` | 阶梯 4 |
| 喂食 | 复刻 `mobInteract` 三步（全 public API），音效用 `SoundEvents.GENERIC_EAT` 替代 protected 的 `playEatingSound` | 无阶梯 |
| 比较器 | `hasAnalogOutputSignal` + `getAnalogOutputSignal(state, level, pos, **direction**)` | 层 9，阶梯 2 |

**没有产生任何 Mixin**，也没有新增 MenuType / 客户端类。整条功能最高到阶梯 4。

### 8.2 实现期确认的两条 26.2 事实（此前 §5 待实测项）

1. **自定义 `Container` 能被原版箱子界面正确同步**：`ServerPlayer` 自带一个 `ContainerSynchronizer`，
   对**所有**它打开的菜单统一 `setSynchronizer`（反编译 `ServerPlayer:276/459`）；
   `AbstractContainerMenu#broadcastChanges` 每 tick 重读每个 `Slot.getItem()` 并推差额（`:196-201`），
   所以**外来改动**（动物吃掉一个）在下一 tick 就同步到开着的界面。实测：界面能开、内容正确。
2. **漏斗本来就兼容，不需要 `WorldlyContainer`**：`HopperBlockEntity#getBlockContainer` 对
   「`state.hasBlockEntity()` 且 `level.getBlockEntity(pos) instanceof Container`」直接取用（`:375`），
   `getSlots` 在非 `WorldlyContainer` 时退回「全部槽位」（`:170-185`），
   `canPlaceItemThroughFace` / `canTakeItemThroughFace` 的判定只在 `instanceof WorldlyContainer` 时才生效（`:298/306`）。
   → 普通 `Container` = 全 27 格、双向、不限面。**原先 wiki 里「漏斗不会把它当容器」的说法是错的，已改正。**

### 8.3 踩坑：改了 `BHR_LangEntries` 不等于语言文件就更新了

第一次进游戏时方块名与界面标题都显示**原始键名**（`block.richards-whimsy-mod.bhr_feeder_chest`）。

原因：`BHR_LangEntries` 是 **datagen 的输入**，不是语言文件本身。真正进包的
`assets/richards-whimsy-mod/lang/{zh_cn,en_us}.json` 要跑 `gradlew syncDatagen`
（内部先 `runDatagen`）才会被重写。只改生成器、不跑 datagen，jar 里就没有那两条键。

另一处细节：26.2 的**方块**与**方块物品**各有独立键，`block.<ns>.<id>` 与 `item.<ns>.<id>` 都需要
（不互相回退），这也是 `LangEntrySupport.addBlockAndItem` 一次写两条的原因。

处理：直接把两条键补进两个语言文件（与生成器输出一致，后续 `syncDatagen` 不会产生差异）。
以后新增方块/物品的标准顺序应是：**改生成器 → `gradlew syncDatagen` → `build`**。
