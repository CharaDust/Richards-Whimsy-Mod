# 03 · 功能重制方案可行性评价

- 分析日期：2026-10-06（Asia/Hong_Kong）
- 对照范围：`doc/wiki/ClassRandomThings/`、`doc/wiki/ClassWhimsyIdea/`，以及对应的 `src/main/java/com/rcdmake/whimsy/block/` 内容。
- 结论性质：迁移方案评价，不是 26.2 API 的逐项迁移实现。

## 结论

直接重制所有已实现功能是可行的，而且对当前项目比逐行迁移更合适；但“直接重制”应定义为：以 wiki 功能规格和资源资产为输入，在 26.2 中重新设计注册、方块行为、客户端渲染和测试，而不是把旧 Java 类逐个机械改名。

建议采用以下组合：

- 架构层面直接重制，不保留旧版类的兼容包袱。
- 功能层面按小批次完成，每批只包含 1 到 3 个相互关联的方块。
- 每批完成后立即编译、生成资源并进行游戏内验收。
- 旧分支 `1.20.4` 作为行为和资源参考；当前 `26.2` 分支作为新实现，不要求两套代码长期共存。

## 为什么可行

这两组功能的复杂度主要在 Minecraft 方块 API 适配，而不在项目业务耦合：

- wiki 当前覆盖 10 个功能条目；鲁米诺条目实际注册 3 个方块，因此共对应 12 个注册方块。
- 每个方块大多拥有自己的类、自己的注册方法和自己的资源文件。
- 跨模块依赖很少，主要公共依赖只有模组 ID、注册表、BlockItem 和客户端渲染初始化。
- 功能行为集中在少量回调：交互、实体碰撞、计划刻、投射物命中、落地、碰撞形状、方块放置朝向和颜色提供器。
- 现有资源已经按稳定的 registry id 组织，例如 `rdt_sugar_glass`、`rdt_quartz_glass`、`wi_aerogel`；如果不主动改 ID，大部分模型、blockstate、语言和纹理可作为重制输入继续使用。

因此，这不是需要保留旧内部实现才能迁移的系统。重制主要是重新表达同一组外部行为。

## 需要先冻结的外部契约

重制前应把下列内容视为不可随意变化的兼容契约：

| 契约 | 当前情况 | 建议 |
| --- | --- | --- |
| 模组 ID | `richards-whimsy-mod` | 保持不变 |
| 注册 ID | 已在源码、资源和语言文件中使用 | 第一轮重制保持不变 |
| 功能名称 | wiki 已定义中文名称和主要特征 | 将 wiki 作为验收规格，而不是只作为历史说明 |
| 资源路径 | 模型、blockstate、语言、纹理已存在 | 先复用，只有格式不兼容时才改路径或内容 |
| 未实现功能 | 多个 wiki 条目标为“未实现”或源码没有对应逻辑 | 明确标为“目标行为”或暂不实现，不能默认为已完成 |

## 当前 wiki 与源码的重要偏差

这些偏差不会阻止重制，但会影响验收，必须在开始实现前决定“保留现状”还是“按 wiki 修正”：

| 功能 | wiki 规格 | 当前源码观察 | 评价 |
| --- | --- | --- | --- |
| 气凝胶 | “稍有阻力地穿过” | `slowMovement` 使用 `Vec3d(1, 1f, 1)`，实际没有明显减速 | 需要确定目标速度系数；重制时应写成可测试的数值 |
| 通灵原木 | 穿过时减速 | wiki 明确标注代码未实现；源码有 `noCollision()`，没有减速回调 | 应作为待实现行为单独验收 |
| 固化水 | 具有原版水颜色，并有后期上色说明 | 源码注册了 block/item color provider；渲染层由客户端初始化设置 | 颜色提供器和水色采样要在 26.2 中重新验证 |
| 糖玻璃 | 踩踏或弹射物破坏 | 源码已实现两种触发；但回调中调用 `super.onSteppedOn`，而不是语义对应的落地父类调用 | 重制时应分别测试玩家、实体、投射物和掉落行为 |
| 垫脚方块 | 放置后 200 Tick 破坏 | 源码使用 `scheduleBlockTick(..., 200)` | 需确认 200 Tick 是 10 秒目标，而不是文档中的“200 秒”注释 |
| 鲁米诺方块 | 纯色视觉渲染、不实际发光 | 源码实际设置 `luminance(state -> 1)`，会参与光照；颜色/纯色自定义渲染未实现 | 这是规格与实现的明确冲突，必须先选定目标 |
| 超级滑滑冰 | 极低摩擦/无摩擦 | 源码通过 `slipperiness(1.0989f)` 近似实现 | 需在 26.2 中用可重复的滑行测试定义验收阈值 |
| 糖块 | 右键恢复饥饿和饱和度并销毁 | 源码已实现服务端交互、声音、统计和破坏 | 行为边界较清晰，可作为首个重制样本 |

另外，`RDT_BlockBreaker` 位于 `ClassRandomThings/BlockEntity/` 并在主入口注册，但类本身继承的是普通 `Block`，不是 Minecraft `BlockEntity`。当前提供的 wiki 条目中没有对应说明。它包含“站立伤害”和“邻居更新时破坏上方方块”两种行为，不能遗漏；应补充 wiki 或明确从本轮重制范围排除。

## 推荐的重制批次

### 批次 A：纯方块属性与资源

先重制超级滑滑冰、鲁米诺方块、糖块。它们分别覆盖基础方块设置、亮度/渲染决策、交互事件，但没有复杂碰撞形状或状态机，适合验证 26.2 注册与资源基线。

### 批次 B：透明方块与碰撞形状

重制糖玻璃、石英玻璃、青金石玻璃、气凝胶和通灵原木。重点验证透明渲染、相邻面隐藏、玩家/其他实体差异化碰撞，以及方块状态 `AXIS`。

### 批次 C：时间与世界事件

重制垫脚方块、固化水和 `RDT_BlockBreaker`。重点验证计划刻、颜色提供器、邻居更新、实体事件及客户端/服务端边界。

每个批次都应保留旧 registry id，并在完成后记录：编译、数据生成、客户端启动、专用服务器启动和实际行为测试结果。

## 不建议的做法

- 不建议先把旧类全部复制成新包，再逐个替换过时 API；这会把旧的空实现、错误注释和规格偏差一起复制过去。
- 不建议一开始同时重写所有 Java、JSON、Mixin 和渲染系统；失败时无法定位原因。
- 不建议把 wiki 中“未实现”描述直接当成已经完成的功能。
- 不建议在第一轮同时改变 registry id、资源路径和行为定义；这会把迁移问题与内容变更混在一起。

## 最终评价

“直接重制所有功能”在架构上可行，且是本项目当前规模下的推荐方向；“阶梯”不应被理解为逐个旧类修补，而应理解为按功能边界分批重建和验收。真正的前置工作不是保留旧实现，而是先把 wiki 中的目标行为、未实现项和当前源码偏差冻结成可测试规格。
